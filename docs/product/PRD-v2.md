## 1. 背景

### 1.1 现状

Github·Tidings 已经上线（<https://tidings.natsukashii.cn>）：每天自动出全站涨星榜（近 1／7／30 天，前 20 含并列），有 Skill 安装榜、热点榜、精选榜、AI 整理的中文项目资料、收藏、安装指令、飞书周报。工程基础比较扎实：211 项测试通过，每天自检，数据可追溯，AI 产出留痕。

### 1.2 问题

所有者的感受是"除了看榜单、复制、推送之外没有别的价值"。原因有三：

1. **价值链太短**：只覆盖"发现 → 读懂 → 收藏／复制安装"，后面的判断（要不要用、和别的方案比怎样、先研究还是先试）全靠用户自己。
2. **只有供给驱动一条路**：手上有具体问题时，没有"从问题出发找工具"的入口。
3. **收藏攒不下决策**：只存仓库，不记为什么收、下一步做什么，也不跟进收藏过的项目后来的变化。

### 1.3 证据（Claude 2026-11-08 核实）

| 事实 | 数据 | 意味着 |
|---|---|---|
| 真实使用量 | 服务器库（11-08 备份）：账号 2 个，**收藏 0 条**，投票 1 票，换卡 0 张；首版验收 #15 未做 | 现有功能还没进入日常使用；升级要先用真实任务验证 |
| 已收录项目 | 约 5,790 个仓库有描述和 topics（涨星候选累积），其中 5,616 个已归类；292 个有完整项目资料 | 检索语料不小，但**偏向"最近涨过星"的项目** |
| 已收录 Skill | 160 个项目的资料里识别出 4,942 个 Skill（有路径和用途说明）；skills.sh 排行 600 条，其中 569 条能对应到 GitHub 仓库，**但都没有说明文字** | Skill 检索要先统一身份；skills.sh 条目只能按名称和来源检索 |
| 运行位置 | 服务器在中国大陆，连不上 GitHub、GH Archive 和 AI 服务；采集和 AI 生成都在所有者的 Mac 上；launchd 每天 09:00–23:45 每 15 分钟叫醒一次，**完整的每日更新一天只跑一次** | 服务器上不能同步调用 AI 或 GitHub；要 Mac 处理的事情是异步的，而且只在 Mac 开机、在运行时段内才处理 |
| 星数接口 | 已在用 GitHub 官方 `stargazers/history`；GitHub 文档写明该接口的周、日边界**不保证与 UTC 对齐**，而榜单按 UTC 统计日计算 | 数据口径有一个没关闭的风险，放进 B0-02 先核对 |

## 2. 定位与目标

### 2.1 定位【调整】

**GitHub 生态情报与能力选型中心**：面向个人 AI 工作流的 GitHub 生态发现、能力评估和工具选型入口。持续发现值得关注的开源项目和 Agent 能力，讲清它们能解决什么问题，帮用户判断值不值得引入，再把决定交给用户自己的 AI（Claude Code、Codex）去研究、试用或安装。英文名仍是 Github·Tidings。

一句话：**不只告诉你 GitHub 上什么火，还帮你判断哪些和你有关、值不值得投入，并把下一步交给你的 AI。**

### 2.2 三个角色

| 角色 | 回答的问题 | 承载能力 |
|---|---|---|
| 生态雷达 | 外面出现了什么值得知道的新变化？ | 客观榜单、近期动态、关注主题、变化雷达 |
| 能力研究员 | 这个项目真正有什么用？适不适合我？ | 项目资料、检索、能力评估卡、定向对比 |
| 行动交接台 | 我要试这个，下一步怎么做？ | 研究／试用／安装三种交接、候选与决策状态 |

不做第四个角色"工具运行管理"：装好以后的管理、Agent 编排、项目执行都不在 Tidings 里。

**关键取舍**：深度研究、试用、安装优先**交给用户自己的 AI**（交接）。Tidings 负责结构化资料、交接模板和决策记录，不在站内另建研究引擎。理由：服务器调用不了 AI 和 GitHub；用户的 Claude Code、Codex 能读代码、搜 GitHub、做受控试用，比站内实现强；而且不另花钱。

### 2.3 价值闭环

```
生态发现 ─┐
          ├─► 理解（资料、评估）─► 决策（候选状态、理由）─► 交接（研究／试用／安装）
需求探索 ─┘                                                        │
          ▲                                                        │
          └──────────── 再发现（变化雷达、关注主题）◄────────────────┘
```

### 2.4 目标

| 目标 | 怎样算做到 | 阶段 |
|---|---|---|
| G1 用起来 | 所有者用三条真实流程走通（第 9.2 节），并开始积累两周的真实使用记录 | P0 |
| G2 能从问题出发 | 对检索测试集（B0-04）里"库里明确有候选"的问题，能把预期候选找出来；库里没有的，不编造，如实说明并能交给 AI 去 GitHub 找 | P0 |
| G3 能判断 | 对一个候选，1 分钟内读懂它能做什么、不能做什么、要什么条件、有什么风险 | **P1**（P0 只做到：交接前提醒用户检查使用条件和权限风险） |
| G4 不遗忘 | 收藏过的项目出现关键变化时，能在站内看到，同一变化只提示一次 | P1 |

### 2.5 设计原则

沿用《产品说明》第 4.2 节的全部原则（榜单客观、数字来自官方、缺失不补零、前 20 含并列、零新增费用优先、AI 产出留痕可切换、只做电脑版、安全边界），再加六条：

1. **四层分开**：客观数据、AI 情报、个人决策、主观精选各占一层，互不改写。AI 和个人判断不能改变客观榜单的排序。
2. **评价要有证据**：AI 评价附出处，不出综合评分。区分"官方文档明确不支持""资料没提到（未知）""实际测试未通过"；没有证据的统一写"未知"，不靠 AI 推测补齐；没实测的只写"文档声称"。
3. **不把"没搜到"说成"不存在"**：检索写明范围和数据日期。0 条结果才说"没找到"；有 1–2 条就如实展示，同时提示"结果较少"。
4. **第三方内容是不可信输入**：README、SKILL.md、Issue 等第三方材料只当资料；里面写的"请执行某命令"不构成任何授权。
5. **热门不等于授权**：试用、安装交接默认先做安全检查；敏感操作要用户确认；条件不满足时停下，不能继续往下做。
6. **服务器是个人数据唯一的业务事实源**：关注主题、候选、使用记录由服务器写入和计算，按账号隔离；Mac 只保存受控备份（服务器库的每日备份）和异步任务需要的最少信息（如任务对象的仓库全名），不在 Mac 上读写或推回这些个人数据。个人数据不进 Mac 生成的公共数据，不进分享页，伙伴之间互不可见。

### 3.1 用户【沿用】

所有者本人（重度 Claude Code、Codex 用户，有多个个人项目）；以后由所有者开通的伙伴，各自收藏、各自决策。不开放注册。

## 4. 核心概念与对象

### 4.1 概念（新增词条同步进 GLOSSARY）

| 概念 | 定义 | 状态 |
|---|---|---|
| 项目 | GitHub 上的一个公开仓库，是发布载体 | 沿用 |
| Skill | 仓库里一个能单独收藏、单独安装的能力包，是实际使用的能力单元 | 沿用 |
| 已收录 | Tidings 本地存有资料的项目和 Skill。项目分**资料级**（有完整项目资料）和**描述级**（只有 GitHub 描述、topics、分类）；Skill 分**资料级**（项目资料里识别出、有路径和用途）和**名称级**（只在 skills.sh 排行里，有名称和来源，没有说明） | 新增 |
| Skill 检索对象 | P0 的最小 Skill 身份，见 4.3 | 新增 |
| 能力关键词 | 归类时顺带产出的中英文关键词，描述能做的事和能解决的问题，只供检索，不显示 | 新增（先小样本验证） |
| 关注主题 | 某个账号主动关注的领域或需求：名称、一句说明、关键词、可选分类、状态（草稿／启用）。只有"启用"的参与匹配 | 新增 |
| 候选 | 收藏升级后的叫法：带决策状态、理由、下一步的收藏对象（项目或 Skill）。界面上仍叫"收藏" | 调整 |
| 决策状态 | 感兴趣（默认）、待研究、已采用、不采用。独立标记，不强制按顺序 | 新增 |
| 交接 | 复制给自己 AI 的结构化任务文字，分研究、试用、安装三种，各有权限边界（6.1 P0-05）；安装交接就是现在的安装指令 | 调整 |

| 变化 | 候选或关注主题相关项目出现的值得注意的事。每条变化只提示一次 | 新增（P1） |

### 4.3 P0 的最小 Skill 检索对象

| 字段 | 资料级 Skill | 名称级 Skill（skills.sh） |
|---|---|---|
| 唯一标识 | `仓库全名#SKILL.md 所在路径` | `skills.sh:<来源>/<skillId>` |
| 名称 | SKILL.md 里的名称 | skills.sh 的 skill 名 |
| 说明 | 项目资料里的用途说明 | 无（界面写"暂无说明"） |
| 来源 | GitHub 仓库 | skills.sh 来源；能对应 GitHub 仓库时一并记下 |
| 详情目标 | 所在仓库的详情栏，定位到这个 Skill | 对应仓库**已收录**时打开该仓库详情栏；否则新窗口打开 skills.sh 页面 |

### 6.0 批次 0：开工前的前置工作

### 6.1 P0：建立第二条使用路径

**P0-01 统一检索（已收录范围）**【新增】

- 检索对象：已收录项目（资料级约 290 个、描述级约 5,800 个）；Skill 检索对象（4.3，资料级约 4,900 个、名称级 600 个，按 4.3 合并去重）。

- 结果数量的三种处理：
  - **0 条**：明说"已收录范围内没有找到"，给出"交给 AI 去 GitHub 找"（P0-05 研究交接，带上用户输入的问题）；
  - **1–2 条**：照常展示，顶部提示"结果较少，可以交给 AI 去 GitHub 找更多"；
  - **3 条及以上**：照常展示，底部常驻"交给 AI 去 GitHub 找"入口。
- 技术约束：服务器端检索，不调用 AI、不调用 GitHub。
- 验收：
  1. 在 B0-04 测试集上：**"库里明确有候选"的问题，预期候选出现在前 10 条结果里的比例 ≥ 80%**（初始门槛，所有者确认测试集时可调）；

  3. 中文、英文、中英混合三类各至少 3 条通过；

**P0-02 能力关键词：先小样本验证，再受控回填**【调整，已确认 D6】

- **阶段 B 受控增量回填**：只有阶段 A 证明关键词提升了测试集结果，才分批回填其余约 5,600 个项目。回填要能暂停、恢复、失败重试，有每日额度上限和进度留痕，不影响每日出榜（错开每日更新运行）。之后新归类的项目都带关键词。

- 留痕同归类；AI 接入功能清单"归类"一行的"写"补上关键词。
- 验收：阶段 A 有对照结论，写进验收记录；阶段 B 只在阶段 A 结论为"有效"时启动，完成率写进日志。不以"生成了多少条关键词"作为成功标准。

**P0-03 收藏任意仓库（#68）**【新增】

- 验收：核对不到的证据丢掉并写明条数；同一项目没有新提交时不重复生成。

**P1-02 变化雷达**
- 监测对象：所有候选（"不采用"的除外）和已启用主题命中的项目。巡检时每个对象多查 1–2 次官方接口。
- 判定规则：
  - **新正式版**：最新正式版和上次记录的不同；
  - **首个稳定版**：第一次出现不带预发布标记、主版本号 ≥ 1 的正式版（1.0 只是一个信号，页面写"首个 1.x 正式版"，不直接写"已稳定"）；
  - **归档**：仓库状态变为 archived；
  - **停更**：超过 180 天没有推送；
  - **涨星异动**：近 7 天新增明显高于此前 4 周的平均水平（具体倍数在实施规格里定）；
  - **README 有较大改动**：哈希变化只作为候选信号，再按变动篇幅判断；只有篇幅变化达到门槛的才由 AI 写一句摘要（"较大改动"的门槛在实施规格里定）。
- 去重：每条变化有身份（对象 + 类型 + 版本或日期），只提示一次；用户看过或忽略后不再出现；同一状态持续（例如一直停更）不每天重复提示。
- 显示：收藏卡上的变化标记、发现页"你的候选有 N 项新变化"；不推送（推送放 P2）。
- 验收：用历史数据回放能识别出每种变化；同一变化不重复提示；没变化时什么都不显示。

**P1-03 Skill 级索引与风险**
- 在 4.3 的基础上补全：所在提交、使用条件、静态风险标记（含可执行脚本、含 hooks 配置、声明网络访问、要求凭据或环境变量）。
- 风险标记只描述"发现了哪些信号"；**没发现不等于安全**，界面和交接里都写"未发现以下信号，不代表经过安全审查"，不能当作安全认证。
- 验收：资料级 Skill 都有风险标记；文案里没有"安全""已审查"之类的表述。

**P1-04 按分类查涨星**
- 两种结果分开标：① "前 20 里属于这个分类的"（过滤）；② "这个分类在全部已核数候选里的前 20"（重新取，沿用完整性下限提示，从第几名起"可能有漏"）。不能把候选不足的结果包装成全站完整榜。
- 验收：两种口径在界面上写清楚。

**P1-05 站内定向对比**【已确认 D4】
- 勾选 2–4 个有评估卡的候选，填一句需求，并排显示各维度和证据，未知项标"未知"。不做通用参数对比平台。
- 验收：所有者用它完成一次真实取舍，并记下做了什么决定。

**P1-06 研究队列**
- 复用 P0 补全任务的协议（7.4），扩展任务类型：深入评估、需求理解等。补齐：任务去重（同一对象同一类型在处理中时不重复建）、优先级（用户主动发起的先于后台的）、每日额度上限（设置页可调）、失败重试和恢复规则。
- 只建队列基础设施和"深入评估"这一个任务类型；GitHub 远程检索作为正式功能放 P2-02，不在 P1 提前建成。
- 验收：Mac 关机时请求不丢；额度用尽时停止并在界面写明；失败的写明原因并可重试。

### 7.4 最小异步任务协议（P0，供补全任务使用；P1 研究队列复用）

**运行方式**：与每日完整更新**解耦**。launchd 每 15 分钟叫醒一次，每次先跑"任务巡检"（拉取并处理待办任务，几秒到几十秒），再判断每日更新是否到点。每日更新正在跑时，任务巡检照常进行，但不和它抢同一个数据文件的写入（实施规格里定锁）。运行时段同 launchd：每天 09:00–23:45；时段外和 Mac 关机时任务留在服务器排队。

**任务字段**：任务 id、类型（P0 只有 `repo_enrich`）、对象（仓库全名，规范成小写）、发起账号、状态、尝试次数、下次可重试时间、失败类型、结果、建立时间、更新时间。

**状态机**：

```
pending ──(Mac 领取)──► processing ──► completed
   ▲                        │
   │                        ├──► failed_permanent（不再重试）
   └──(到达重试时间)── failed_retryable ◄─┘
```

- Mac 领取任务时把状态改为 `processing`，并记下领取时间；超过 30 分钟仍是 `processing`（Mac 中途关机或崩溃）的，视为没领取，退回 `pending`。
- **失败分类**：
  - `not_found`（仓库不存在或不公开，GitHub 明确返回 404）→ `failed_permanent`，收藏卡标"仓库不存在或不公开"；
  - `rate_limited`（限流）、`network`（网络故障、超时）、`upstream`（GitHub 5xx）→ `failed_retryable`，按退避时间重试（如 15 分钟、1 小时、6 小时），最多 5 次，用尽后转 `failed_permanent` 并标"多次补全失败，可手动重试"；
  - 临时故障不能写成 `not_found`。
- **幂等**：同一对象同一类型已有 `pending`／`processing` 任务时，不再新建，直接复用；同一账号重复收藏同一仓库不建重复收藏；回写结果按仓库 id 覆盖，重复回写结果一致。
- **结果回写**：Mac 处理完把基本资料推回服务器，服务器写进该仓库的描述级记录并**立即更新检索索引中的这一条**；收藏卡和全站检索同时可见，不会出现"收藏卡已补全、检索搜不到"。
- **索引合并**：服务器上的检索索引由两部分组成：Mac 每日推送的公共索引，加上服务器由补全任务写入的增量记录（单独存放）。查询时两部分合并，同一仓库以较新的那份为准。Mac 推送公共索引只替换公共部分，不删除也不覆盖增量部分；之后某天这个仓库进了公共索引，增量记录可以在确认公共索引已含该仓库后清理。验收测试见 B0-03。
- **可观察**：设置页"数据源"分区显示任务队列：排队 N、处理中 N、失败 N，以及最近一次巡检时间；健康检查（`bin/health.js`）报出超过 24 小时仍未完成的任务。

**验收**：Mac 在线、离线、重启、请求重复、GitHub 临时失败五种情况下，任务都能正确恢复，不丢收藏，不重复建对象（每种都有测试）。

## 9. 成功衡量

### 9.1 指标（个人产品，不看 DAU）

| 维度 | 问题 | 观察指标 |
|---|---|---|
| 需求匹配 | 检索能找出相关候选吗？ | 测试集命中率（P0-01 验收）；日常检索后点开或收藏的比例 |
| 发现效率 | 比刷自媒体更容易找到新能力吗？ | 每周新增候选数 |
| 决策效率 | 能较快判断值不值得研究吗？ | 候选从"感兴趣"走到明确状态的比例 |
| 行动价值 | 多少候选交给了 AI？ | 交接次数／候选数 |
| **真实价值** | 交接后真的解决问题了吗？ | **候选被标为"已采用"或"不采用"且写了理由的数量**（不把"复制了交接"当成功）；P0 三条流程的验收记录 |
| 长期价值 | 旧收藏后来又发挥价值了吗？ | 变化提示后重新打开的次数（P1） |
| 信息质量 | 资料准不准？ | 所有者发现的事实错误和纠正次数 |
| 推送效率 | 收到的值得打开吗？ | 周报点进次数（按 `?from=weekly` 计） |

现阶段不设转化目标。

### 9.2 P0 验收：三条真实流程

所有者用自己的真实需求完成，结果记进 issue：

1. **从榜单发现**：在发现页或涨星页看到一个项目 → 读懂 → 收藏为候选并写理由 → 研究交接给 AI → 根据结论改状态。
2. **从问题出发**：输入一个正在解决的真实问题 → 在已收录里找到候选，或者走"交给 AI 去 GitHub 找"→ 把找到的仓库收藏进来（含榜单外的，等补全完成）→ 定向对比交接 → 定下采用或不采用并写理由。
3. **从收藏重新评估**：打开收藏页 → 按状态找到一个"待研究"的候选 → 换浏览器也能找回 → 交接试用（验证试用交接会先确认环境）→ 更新状态和下一步。

三条都走通，P0 才算完成；任何一步卡住都记成问题，修完从卡住的那条流程重走。

## 14. 边界与明确不做

| 系统 | 职责 |
|---|---|
| Github·Tidings | 外部项目和第三方能力的发现、评估、候选决策、交接 |
| 数码世界（个人 AI 工作台） | 自建 Skill 的展示，个人 Agent 资产和工作流的组织 |
| 猛鬼兽（Hermes） | 授权范围内的主动推送、提醒、执行编排（周报、健康检查、以后的条件提醒） |
| Claude Code、Codex | 研究、试用、安装、开发的实际执行 |
| GitHub 原生 | 代码、Issue、PR、版本的事实来源 |

**明确不做**：公开社区、社交评分、综合推荐指数、付费工具市场、全自动安装、安装后遥测、通用 Agent 编排、项目管理看板、知识图谱、自动读取私人项目资料、站内 AI 聊天窗口、手机版、开放注册；赞踩维持现状，不扩展排行或社交机制。

**沿用的首版不做**：个性化推荐算法、评论、笔记、关注（被"候选"和"关注主题"取代）、外部报道。
