## 2. 背景与问题

### 2.1 起因（所有者原话整理）

想知道近期有什么好项目，现在要去刷小红书、抖音上关注的自媒体的说明视频。想自己做一版最权威的，不用刷别人，打开网页就能看到最近有什么好用的、具体能做什么。

### 2.2 真正的痛点

梳理中所有者明确：痛点**不是自媒体不准**，而是：

1. **慢**：自媒体整理、剪视频、发布，信息到手时已经过了好几天；
2. **要刷到才能看到**：不主动去刷就不知道。

查证时还发现（2026-10-23）：所有者提供的四张自媒体榜单全是周榜；一张明写"非全站排名"，一张混入了 Gist（不是仓库），两张只看 AI 项目。也就是说，现有渠道在"及时"和"全"上都有缺口。

### 2.3 三条标准

所有者定的三条：**一要准，二要全，三要看得懂**。

- **准**：数字来自 GitHub 官方，排序不掺人工判断；拿不准的标出来，不补零、不伪造。
- **全**：GitHub 全站公开项目，不只 AI，不只 Trending；组件库、数据库火了也要。只有离得太远的（如游戏引擎）归"其他"，靠分类筛掉，不从采集里排除。
- **看得懂**：每个项目只需要两样——**一句话说清它是干什么的**，**能帮我解决什么具体问题**。

## 3. 用户与使用路径

### 3.1 目标用户

| 阶段 | 用户 | 说明 |
|---|---|---|
| 现在 | 所有者本人 | 重度使用 Claude Code、Codex 的个人 AI 工作流用户 |
| 以后 | 所有者开通的伙伴 | 看同一份内容，各自收藏、各自投票；不开放注册 |

不面向公众，不做社区、不做内容平台。

### 3.2 使用路径（到此为止）

```
看到最近什么火、有什么变化 → 知道它是干什么的 → 判断对自己有没有用 → 复制安装指令交给自己的 AI 装好
```

**边界**：装好之后用得怎么样完全不追踪。中心只负责"阅读、挑选"这一段。

### 3.3 典型场景

1. **每天花几分钟扫一眼**：打开网站 → 发现页看精选和热点 → 涨星页看近 1 天涨得最快的前 20 → 点开感兴趣的项目读详情栏。
2. **每周被动收到**：周一 19:30 飞书私聊收到"本周涨星前 10"卡片，不用打开网站也知道这周什么火。
3. **决定装一个 Skill**：详情栏里挑出仓库内某个具体 Skill → 选 Claude Code 或 Codex → 复制安装指令 → 粘贴给自己的 AI，由它照项目文档装好、调用一次确认能用。
4. **留着以后再看**：收藏项目或单个 Skill，换电脑、换浏览器登录后还在。
5. **给别人看一眼**：导出一个只读分享页（单个 HTML 文件），发给别人直接打开。

## 4. 价值主张与设计原则

### 4.1 和现有渠道比

| 渠道 | 问题 | 本产品怎么做 |
|---|---|---|
| 自媒体视频、图文 | 慢；要刷到；多为周榜；常只看 AI；口径不统一 | 每天自动出榜；周报主动推送；全站范围、客观口径 |
| GitHub Trending | 每次二十几个项目；排序规则不透明，不是纯涨星 | 只当候选来源之一，不直接当涨星榜 |
| Star History 等单项目工具 | 要先知道项目名才能查 | 全站找候选，自动排名 |
| 第三方"多源周榜" | 非全站；更新慢 | 全站事件数据找候选 + 官方数据核数，每天出榜，带完整性自检 |
| 读英文 README | 费时，看不出"对我有什么用" | AI 从项目原文整理中文的一句话、主要用途、使用场景、使用条件 |
| 自己摸索安装 | 每个项目装法不同 | 生成一段带规则的安装指令，交给自己的 AI 去装 |

### 4.2 设计原则（已确认，审核时请当作约束）

1. **榜单客观**：涨星榜、历史榜、热点榜都不掺人工判断。唯一的主观名单是**精选榜**，单独成块、明确标识（2026-11-03 所有者确认的范围变化）。
2. **数字来自官方**：事件数据只用来找候选，绝不把事件计数当涨星数展示。
3. **缺失不补零、如实标注**：缺数据留空位写"暂缺"；自检不过标"可能不完整"；更新失败保留上次结果并写真实日期和原因；AI 资料没生成写明，不编。
4. **前 20 含末位并列**：网页每个涨星榜前 20，末位同分的一起显示。
5. **零新增费用优先**：数据源全部免费；AI 生成用本机已登录的 Codex、Claude 订阅额度，不调用按量计费的 API；要花钱先问所有者。
6. **AI 产出可追溯、可切换**：每条 AI 产出记下执行方、接入方式、模型、时间；执行方在设置页切换，不改代码（全局规则 P-13）。
7. **只做电脑版**：不做手机适配。
8. **安全边界**：不提交凭据、真实运行数据库、原始响应；不启用云端采集、付费资源或公开发布，除非所有者另行授权。

## 6. 功能说明

### 6.1 全站共用

- **导航**：发现（`/`）、涨星（`/stars`）、收藏、设置。旧链接（`/daily`、`/categories`、`/new`、`/top`、`/trending`、带 `?w=` 的旧首页）都自动跳转，不报错。
- **品牌**：Github·Tidings，"报徽"图标（海面升起一颗星），衬线斜体字标。
- **视觉**："白雾"风格：GitHub 色系、Primer 式控件；浅色 ASCII 鲨鱼背景铺满全屏，上面一层中间浓四周淡的白雾。信息密、细，不做大而空。
- **报头**：四页尺寸一致，切页不跳；左边小字 + 38px 中文大标题（后压一行淡蓝英文装饰：Rising／Boards／Clippings／Settings），右边一排只读读数。
- **三种标签**（全站统一）：
  - **说明标签**：2–6 个字说明领域或用途，如"逆向拆解""私人影音"，每项目一个；
  - **定义标签**：项目是什么，固定 9 选 1：Skill、MCP、Agent、AI 应用、插件、框架、工具、应用、内容，各有类型色；
  - **状态标签**：每项最多一个，优先级 蝉联第一 N 期 ＞ 首次上榜 ＞ 飙升 N 名（≥5 名）＞ 在榜 N 期。
- **分类**（9 个，用来筛选，不改排序）：AI 应用工具、Agent／MCP、工作流自动化、知识管理与办公效率、Skill、开发框架与组件库、数据库与数据工具、开发者工具与基础设施、其他。一个项目最多 2 个分类，由 AI 按项目说明归类。
- **详情栏**：在涨星页、发现页点项目，从右侧滑出；内容与项目页 `/p/作者/仓库` 同一份。
- **动效**：原生脚本 + 浏览器自带 Web Animations，只动 transform 和 opacity；系统开"减少动效"时统一关闭。

### 6.2 发现页（首页 `/`）　【已上线】

一页三块：上面精选榜，下面历史榜、热点榜左右各半。

**精选榜（唯一的主观名单）**

- 按"精选标签"分组，本机库里当前 5 个标签（线上以服务器库为准）：多 Agent 协同、编程技能、创作与设计、本地模型与记忆、实用工具（每个标签有一句判定说明，例如"编程技能"不收教程、课程、面试题）。
- 每个标签固定 7 张卡，一个项目可以出现在两个标签里。
- 默认填法：AI 执行方按标签清单给候选池项目建议标签（参考简介和 GitHub Topics），每个标签按总 Star 填满 7 张（候选池见第 7.5 节）。
- 所有者可以用"⇄"换卡：搜仓库名或粘贴 GitHub 地址；本地没数据时可"联网查 GitHub"一次，查到就换进来。换过的卡固定下来；可"恢复成按星数前 7"。
- 赞、踩：每人各投各的，所有人看到总数，自己投过的高亮、可撤回。
- 权限：标签清单和换卡只有所有者能改，伙伴只能投票；标签清单首版没有页面编辑入口。
- 形态：景深轮播（中间一张正对，左右叠压斜转），"说明书卡"写一句话、最多 3 条"能做什么"、类型／总 Star／Skill 数；← → 切换；可复制当前卡的安装指令。

**历史榜（Skill 安装量）**

- 数据来自 skills.sh 全时段排行榜（每天解析一次公开首页；条款鼓励合理使用和自存缓存，robots.txt 允许该页）。
- 按累计安装量排前 50 个"来源"：同一 GitHub 仓库或网站的多个 Skill 合成一行（如飞书 lark 全系列），按其中最高的安装量排；同一套 Skill 放在几个来源（Skill 名单 80% 以上相同）的也并成一行。
- 栏内先见 20 行，其余栏内滚动。可按分类筛选，筛选后保留原名次。
- 点 GitHub 来源打开所在仓库的详情栏；网址来源（如 open.feishu.cn）新窗口打开 skills.sh 页面。

**热点榜**

- 每天从 Hacker News（官方搜索接口）、V2EX（公开接口）找指向 GitHub 仓库的帖子，按点赞数＋评论数算热度，排前 15。Reddit 未接（要先注册免费应用凭证）；X 不接（没有免费读取接口）。
- 每行带近 7 天热度折线和比昨天涨跌；走势不满 7 天时页面写明；过去没存快照的日子按那天北京 18:00 回推补录，并写明哪几天是补录的。

### 6.3 涨星页 `/stars`　【已上线】

- **三个窗口**：近 1 天（默认）／近 7 天／近 30 天，按 GitHub 统计日（美国太平洋时间）累计。
- **前 20 含末位并列**；按期间新增 Star 排序。
- **报头读数**：数据日期与"数据已更新／未更新"（原因放悬停说明）、第一名、新面孔（上一期不在前 20 的头像）、飙升最多、最多的类型；底边一条类型构成细条，点哪段就按那个定义标签筛选。
- **前三卡 + 第 4–20 名的行**：头像、项目名（作者小字）、一句话、说明标签、定义标签、新增 Star、总 Star、状态标签、名次变化（▲n／▼n／新进／持平）、近 30 天每日新增柱图（缺数据留空位，不补零）。
- **名次变化与连续上榜**：和上一期比；连续 N 期第 1、连续 N 期前 20（N≥2，缺一期断开）；没有可比的上一期就写提示条。
- **完整性提示**：每日自检不过时，当天榜单标"可能不完整"并写出漏失概率。
- **更新失败**：保留上次快照，写真实日期和原因。
- **筛选**：只按定义标签筛（报头底边的类型构成色带可点）。按分类筛只在发现页的历史榜上。
  - 说明：10-24 曾做过"分类涨星榜"（每个分类在已核数候选里取前 20，低于完整性下限的标"可能有漏"），11-03 白雾重设计后界面上不再出现；后台仍每期另存已核数候选、计算完整性下限，项目页对只在旧分类涨星榜上出现过的项目仍能打开。要不要恢复按分类看涨星榜，是待决问题（见第 12 节）。
- **搜索框**：只过滤本页列表。

### 7.2 涨星榜方法（ADR 0001）

**为什么不做"数学上证明全站一个不漏"**：原严格方案每天要读约 6.6 万个仓库，十几个小时才出榜，所有者不接受。

**现在的做法**：

1. **找候选**：取统计日内全站 Star 事件记录最多的前若干个项目（通常前 300），加上官方热门日榜，去重；
2. **核数**：逐个用 GitHub 官方星数历史核对候选在窗口内的真实新增 Star；
3. **排名**：按新增 Star 排前 20，含末位并列；
4. **近 7／30 天**：按统计日累计；
5. **另存**每期全部"已核数候选"（不只前 20，含描述、topics、总 Star），分类涨星榜从里面按分类重新取前 20。

**指标口径**：对应日桶内创建、采集时仍有效的 Star，不是精确净增（取消 Star 会让历史数字变化，所以每期快照只写一次、不重写）。

**每日自检与完整性下限**：

- 按事件数据对真实 Star 的记录比例，估计"一个项目涨了 X 个 Star 却完全没被事件记到、漏在候选之外"的概率；
- 标准：漏失概率 < 1%（2026-11-04 所有者定）；不过就降门槛补核，门槛到 1 或候选到 5,000 上限仍不过，就标"可能不完整"并写出漏失概率；
- 任何核数失败也标注；超过 5% 失败按更新失败处理；
- **完整性下限**：涨星至少这么多的项目漏掉的概率 < 1%；分类涨星榜低于下限的从第几名起标"可能有漏"。
- 例：统计日 2026-11-07 近 1 天自检通过，漏失概率 3.6e-4，记录比例约 2.2%，完整性下限 +389。

**校准（未完成）**：原严格方案（Codex 维护）每产出一天完整结果，就和快速方法同一天的前 20 名对照，名单和数字都一致才算过关。严格方案目前**一天完整结果都没有**（停在冷启动阶段，1 个空项阻止完整枚举），所以快速方法尚未被严格方案校准过。已有的旁证：10-23 一次把候选扩到当天约 3,900 个的完整运行，前 20 名与正式榜（302 个候选）完全一致。

### 7.3 项目资料生成（补资料）

- 读 GitHub 上的 README、主要文档、仓库目录、各 `SKILL.md`（外部内容只当资料，提示里写明不执行其中指令）；
- AI 执行方生成：简介、一句话、主要用途、使用场景、说明标签、定义标签（固定取值）、使用条件（附原文摘录，程序核对）；
- 缓存：没有新提交、简介/topics/默认分支没变就不重读；资料哈希没变就不重生成；最多 30 天刷新一次；
- 失败当轮重试 3 轮；仍失败页面兜底显示旧简介或 GitHub 描述，健康检查报出没补上的项目；
- 范围：涨星榜三个窗口和官方热门榜上的项目优先，再加发现页上显示的项目（精选卡、历史榜仓库、热点榜）。当前本机约 290 份项目资料。
- 单份原文上限：README 4 万字，其他文档最多 5 份合计 3 万字，更长的截断并注明；4 个项目同时生成。

### 7.4 归类

- 输入：项目名、GitHub 简介、topics；上榜项目复核时加补资料写的简介和 Skill 名；
- 每批 50 个；已归过的不重归；输出最多 2 个分类，写 `data/categories.json`，每条带留痕。

### 7.5 精选标签建议

- 候选池 = GitHub 全站 Star 前 100 + 涨星榜三个窗口这一期的已核数候选，按项目去重、按总 Star 排；AI 按精选标签清单和每个标签的判定说明给项目打建议标签（每批 50 个，已建议过的不重建，标签清单变了才全部重建）；
- Mac 先拉服务器的标签清单和已固定的卡，算完写 `pick-pool.json` 推上去，服务器写库并补卡；所有者能看到每张卡是哪个执行方建议的。

## 8. 每日运转

每天北京时间 09:00–23:45，Mac 的 launchd 每 15 分钟叫醒一次；到了设置里的时间（默认 18:00）且当天没跑过就开跑，同一天只整套跑一次。有步骤失败的，上次跑完满 30 分钟后再跑一次，只跑失败的步骤和后面要用它结果的步骤；当天最多重试 2 次，北京 22:00 起不再试，之后等第二天（#94）。为什么不能早于 17:00：GitHub 统计日按美国太平洋时间，北京 16:00 才结束（夏令时 15:00），GH Archive 最后一个小时文件还要再晚约 1 小时（#83）。

| 顺序 | 步骤 | 命令 | 产出 |
|---|---|---|---|
| 1 | 出榜 | `bin/rank-day.js` | 近 1／7／30 天涨星榜快照、已核数候选、新项目榜、官方热门榜、status.json；出完最近一期，再补前 5 个统计日里涨星榜缺的期次（#103） |
| 2 | 全站 Star 前 100 | `bin/history.js` | 精选榜候选池 |
| 3 | 历史榜（Skill 安装量） | `bin/skills.js` | skills.sh 排行快照（设置里关掉 skills.sh 则整步跳过） |
| 4 | 热点榜 | `bin/hot.js` | 热度快照（HN、V2EX 都关则跳过） |
| 5 | 精选榜 | `bin/picks.js` | 精选标签建议、pick-pool.json |
| 6 | 补资料 | `bin/profiles.js` | `data/profiles/<id>.json` |
| 7 | 归类 | `bin/classify.js` | `data/categories.json` |
| 8 | 周报 | `bin/weekly.js` | `data/weekly/<统计日>.*` |
| 9 | 校准报告 | `bin/calibrate.js` | 与严格方案对照（目前无可对照结果） |
| 10 | 推到服务器、备份库 | `bin/push.js` | rsync 推数据；服务器库备份回 Mac，留 14 份 |

外部自检：猛鬼兽每天 09:50 跑 `node bin/health.js`：每日更新多久没跑、有没有卡住或失败的步骤、服务器网站在不在、库备份是否超过 2 天、选定 AI 执行方能不能用、涨星榜前 5 天有没有缺期（#103）；没问题不输出。

## 9. 系统架构与部署

### 9.1 总体

```
            ┌──────────── Mac（所有者电脑）────────────┐
GitHub/GH Archive/ClickHouse/skills.sh/HN/V2EX ──► 每日更新（launchd 定时）
                                                   │  出榜 → 补资料 → 归类 → 周报 …
            Codex / Claude 本机 CLI  ◄───────────────┤  （AI 生成）
                                                   ▼
                                       data/（JSON 快照 + SQLite）
                                                   │ rsync 推送（只增改不删）
                                                   ▼
            ┌──────── 阿里云轻量服务器（中国大陆）────────┐
            │ Caddy（HTTPS）→ Node 网站（127.0.0.1:5310） │ ◄── 浏览器（所有者、伙伴）
            │ center.db：账号、收藏、精选、投票            │
            └──────────────────────────────────────────┘
                                                   ▲
            猛鬼兽（Hermes）读 settings.json / 周报卡片 → 飞书私聊
```

**为什么采集在 Mac**：大陆服务器连不上 GitHub、GH Archive、OpenAI；Mac 关机时网站照常打开，显示最后一次推上去的数据。

### 9.2 数据归属（谁写什么）

| 数据 | 谁写 | 同步方式 |
|---|---|---|
| 榜单、快照、候选、资料、归类、周报、status.json | 只有 Mac | 每日更新最后一步推上去 |
| settings.json | 服务器设置页 | 每日更新开头从服务器拉回 Mac |
| center.db：账号、会话、收藏、精选标签、换卡、投票 | 服务器网页 | 不推、不覆盖 |
| center.db：精选候选池与 AI 建议标签 | Mac | 经 pick-pool.json 推上去由服务器写库 |
| 服务器 center.db 备份 | Mac 拉回 | 每天一份，留 14 份 |

### 9.3 技术栈

- 后端：Node.js 24（ESM，原生 `node:test`），无框架 HTTP 服务；SQLite（WAL）；数据大多是按日期落盘的 JSON 快照。
- 前端：服务端把数据嵌进页面，原生脚本 + Web Animations，不引入 React 和动效库（ADR 0002）。
- 部署：阿里云轻量服务器、systemd、Caddy 自动 HTTPS；GitHub Actions CI 在 PR 和 main 上跑测试。
- 测试：`npm test` 211 项全部通过（2026-11-08）。
- 主要命令：`npm run update`（每日更新）、`serve`、`account`、`share`、`ai`（打印 AI 接入现状）、`calibrate` 等。

### 9.4 AI 接入（按全局规则 P-13）

| 功能 | 执行方 | 接入方式 | 读 | 写 |
|---|---|---|---|---|
| 补资料 | 跟随默认或单独指定 | 本机 CLI | README、主要文档、仓库目录、SKILL.md | `data/profiles/<id>.json` |
| 归类 | 同上 | 本机 CLI | 项目名、简介、topics（复核加资料简介、Skill 名） | `data/categories.json` |
| 精选标签建议 | 同上 | 本机 CLI | 候选池项目简介、topics、标签清单 | `pick_pool` 表 |

- **执行方**：Codex（`codex exec`）、Claude（`claude -p`），都用本机已登录的订阅额度。在空临时目录里跑，不给执行命令的工具，不加载 MCP 和插件。
- **默认执行方三选一**：只用 Codex／只用 Claude（用不了就报错退出，指向设置页，不换家）／Codex 优先·Claude 接力（默认；Codex 失败那次改用 Claude，一次更新里连续失败 3 次剩下的全交给 Claude）。
- **可用状态**：每次跑 AI 功能前检查（可用／未安装／未登录／最近调用失败），存 `data/ai-status.json` 推上服务器给设置页显示。
- **留痕**：每条产出记 `ai: { by, via, model, at, relayed? }`；Claude 记具体模型，Codex 输出里没有模型名记 null（页面写"默认模型"）。
- **对外开放**：猛鬼兽只读本机文件、跑本机命令，不写本应用数据；MCP 未开放（规划中）。
- **数据对象**：无。
- 不是 AI 功能：安装指令（模板拼接）、校准与每日自检（统计计算）。

## 11. 已知限制与风险

1. **完整性不可证明**：事件数据只记到真实 Star 的约 1–4%，被严重漏记的项目可能漏榜；靠自检标注兜底，严格方案校准尚未生效。
2. **依赖免费第三方数据**：GH Archive、ClickHouse、skills.sh（解析公开页面，非正式接口）任何一个变化都可能让当天更新失败；处理方式是保留上次结果并写明。
3. **GitHub API 额度**：每小时额度有限，扩大候选、补资料、Release 查询都在抢额度。
4. **AI 订阅额度**：Codex 额度用尽时靠 Claude 接力；两家都不可用就报错，资料停在旧版。
5. **单点在 Mac**：Mac 关机、睡眠、重启都会让当天更新延后或错过；网站仍可看旧数据。
6. **服务器在大陆、域名未备案**：访问可能被拦。
7. **AI 生成质量**：简介、用途、分类是 AI 从项目原文整理的，未逐条人工核对；使用条件有原文摘录核对，其他字段没有。
8. **历史指标口径**：Star 被取消后历史数字会变；每期快照只写一次，不追溯修改。
9. **前端无框架**：页面变多、交互变复杂后维护成本会上升（ADR 0002 已预留重新讨论）。

## 13. 术语速查

| 术语 | 含义 |
|---|---|
| 项目 | GitHub 上的一个公开仓库 |
| Skill | 仓库里能单独收藏、单独安装的能力包，一个仓库可包含多个 |
| 涨星榜 | 按一段时间新增 Star 对全站项目客观排出的名单 |
| 历史榜 | 现指 Skill 安装量前 50（skills.sh），按来源合并 |
| 热点榜 | 按 HN、V2EX 讨论热度排的前 15 |
| 精选榜 | 所有者按精选标签人工挑选、伙伴可赞踩，每标签 7 张 |
| 已核数候选 | 某期涨星榜里用官方星数历史核过新增的全部候选 |
| 完整性下限 | 涨星至少这么多的项目漏榜概率 < 1% |
| 统计日 | GitHub 统计日（美国太平洋时间）：官方星数日桶按太平洋时间分日，北京 16:00 结束（夏令时 15:00），日终即定稿。#83 前误作 UTC 日、北京 10:00 出榜，那些期最后一天没数完，页面按出榜时刻自动标注 |
| 项目资料 | 从项目原文整理出的简介、一句话、用途、场景、标签、使用条件、Skill 列表及依据 |
| 详情栏 | 点项目从右侧滑出的栏，内容同项目页 |
| 执行方 | 真正产出 AI 内容的一方：Codex 或 Claude |
| 接力 | Codex 失败时改用 Claude 重做（只在选了该项时） |
| 留痕 | 每条 AI 产出记下的执行方、接入方式、模型、时间 |
| 分享页 | 四页只读副本，单个 HTML 文件 |

完整术语见 `GLOSSARY.md`。
