# 开发实录与坑

踩过的坑记在这里，Claude 和 Codex 都读。排障、发布、改脚本之前，先搜一遍：`grep -n 关键词 docs/LESSONS.md`；换个项目也成立的坑在全局 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`（G-xx），也搜一遍。

## 怎么写

- 每轮交接时自问「本轮踩到新坑了吗」：有就在下面追加一条，并在 CURRENT.md 的交接里写「本轮新坑：L-xx」；没有就写「无」。
- 一条一个坑，编号只增不改。写现象、根因、正确做法、证据。证据写到能查的程度（提交号、文件与章节、证据目录）；查不到就写「未核实」，不编。
- 结论被推翻时改条目并注明日期，不删。

## 怎么升级

- 同类坑第 2 次出现：把正确做法写进 AGENTS.md 或 docs/OPERATIONS.md（一句话硬约束进 AGENTS.md，操作细节进 OPERATIONS.md），条目的「升级」改成写到了哪里。
- 能用机器判定的：写成测试或脚本（如 `scripts/check-rules.mjs`），条目注明。
- 换个项目也成立的（不依赖本项目的业务、页面、发布脚本）：提议提升到全局坑 `/Users/nat/Documents/ChatGPT/个人/work/agent-kit/LESSONS.md`，写成 G-xx；原条目保留，末尾加一行「提升：已提升为全局 G-xx（日期）」。只出提案，用户批准才写。
- 条目超过约 30 条时整理一次：已升级、且之后没再犯的，归档到 `docs/history/`。
- 「升级」一行每条都要有，开头写层级词〔结构〕〔机检〕〔体检〕〔文字〕〔提醒〕之一，再写状态（未升级 / 不升级 / 部分升级 / 已升级）、日期、编号和去处；还没升级的写「〔提醒〕未升级。」。层级的含义和怎么选，以全局 LESSONS「怎么升级」为准。起步骨架的 `scripts/check-rules.mjs` 能查这一行（本仓库还没装）。

## L-01 缺数据、读不全、生成失败时页面不照实写：「缺失不补零」写在 AGENTS.md 里，审查仍一张张查出来（2026-10-23 至 10-24）

- 现象：批次 A、B 的两轴审查里，至少 7 张 issue 被查出同一类问题：缺的那周按 0 算、整张走势隐藏、旧文档的简介当新的显示、只读了 30 个 Release 就说「没发」、没资料的项目写「简介生成中」、读不到的项目信息悄悄丢掉、总 Star 写「暂缺」和别页对不上。每次只修被点名的那一处。
- 根因：「缺失不补零」从第一个提交起就在 AGENTS.md，但只是一句原则；各处渲染和统计直接拿裸值（数字、字符串），取不到时各自兜底成 0、空串或旧值，没有一个地方逼着写「为什么没有」。
- 正确做法：
  - 取数函数返回「值，或缺失原因（没查全 / 失败 / 不适用 / 还没生成）」，页面、周报、飞书消息按原因写明，不兜底成 0、空或旧值。
  - 新功能交审前，自己先按「数据缺一周、接口失败、读不全、项目不在榜上」四种情况各看一次。
  - 修一处时搜同一份数据的其他展示位置（网页、周报、飞书、设置页），一起改。
- 证据：两轴审查修复提交 `2ecf26e`（#2）、`75a2491`（#6）、`bc83f50`（#8）、`1545585`（#13）、`ddefc18`（#14）、`b473b79`（#11）、`56d0cca`（#10）；AGENTS.md 第 7 行（首个提交 `8ad4606` 起就有）。
- 升级：〔文字〕部分升级：AGENTS.md「缺失不补零」从首个提交就在，写了仍再犯 7 次；最硬能升到〔结构〕：渲染只接受「值或缺失原因」对象（复盘第六节），未做。
- 触发：`补零`、`暂缺`

## L-03 按标签把 GitHub 官方星数日桶当成 UTC 分日，每天出榜时最后一天还差 6 小时没数完（2026-11-03 发现苗头，11-08 实测定论）

- 现象：11-03 首页新鲜度按 UTC 零点算，北京 20:00 以后最新一期也显示「已 1 天没有新数据」（`075aaf2` 修）。11-08 实测发现官方日桶其实按美国太平洋时间分日：每天北京 10:00 出「昨天」的榜时，那一天还差 6 小时，最后一天中位少数两成多；按新窗口重出 11-07，前 20 里 11 个名次变了。
- 根因：官方 `stargazers/history` 的 `week` 时间戳正好是周日 00:00Z，就据此认定「按 UTC 划分」，没去实测日桶什么时候出现、什么时候停涨；文档只写「不保证与 UTC 对齐」。
- 正确做法：依赖外部数据的日界、时区、何时定稿的，先轮询实测（看新的一天何时出现、旧的一天何时停涨），结论和证据写进 ADR；只看标签或时间戳格式不算证据。夏令时这条是推算，2027-03-14 切换后要再核一次（ADR 0001 第 4 节）。
- 证据：`075aaf2`（#39）；`docs/adr/0001-fast-star-ranking.md`「2026-11-08 补充」第 3、4、6 节；`7552616`（#83，PR #84）。
- 升级：〔结构〕部分升级（2026-11-08，#83）：统计日只在 `src/ranking/stat-day.js` 一处按 `America/Los_Angeles` 算；日界前生成的榜首页自动标「最后一天未数完」（`src/web/home.js`）。不覆盖：别的外部数据源的日界，以及夏令时那条推算。
- 触发：`stargazers/history`、`stat-day`

## L-06 外部请求没设超时，连接挂住后进程空等 8 分钟一个响应都没收到（2026-10-23）

- 现象：真实出榜运行中进程空等 8 分钟，没收到任何响应，也没报错。
- 根因：官方接口和数据源请求没有超时，连接挂住就一直等；同时并发 6、每分钟约 780 次请求，接近 GitHub 每分钟 900 次的次级限流。
- 正确做法：服务端每个外部请求都带超时（`AbortSignal.timeout`，出榜管线 60 秒），超时算失败并重试；并发按对方限流留余量（这里降到 4，约每分钟 500 次）。
- 证据：`3e03be0`（#3）；当前各处 `fetch` 的 `signal` 在 `src/ranking/sources.js`、`src/ranking/github.js`、`src/profiles/update.js`、`src/boards/*.js`、`src/web/repo-lookup.js`。
- 升级：〔提醒〕未升级。超时在各调用处各写一份；最硬能升到〔机检〕：测试扫 `src/`、`bin/` 里服务端 `fetch(` 没带 `signal` 的就失败，未做。
- 触发：`/await fetch\((?![^)]*signal)/`
