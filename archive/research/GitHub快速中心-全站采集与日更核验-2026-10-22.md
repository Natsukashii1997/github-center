# GitHub 快速中心：全站采集与每日运行核验

核验日期：2026-10-22。交付性质：可行性研究与隔离实测，不是产品上线或每日运行验收。

**结论：已完成一次近 30 个统计日的完整候选核验；免费采集路线有实证，但“完整日／周／月三榜每天稳定更新”尚未验证。主要瓶颈是日榜覆盖所需的请求量，而不是页面展示或 AI 日报生成。**

本轮没有安装软件、购买服务、创建或公开仓库、上传凭据、部署网站或注册定时任务。

## 1. 当前已经确认的产品口径

- 统计范围是 GitHub 全站公开仓库，包含 fork，不缩减为人工精选池或收藏池。
- 按 GitHub 官方统计日桶计算近 1／7／30 日，每天更新。
- 三张涨星榜各展示 Top 20，包含第 20 名的全部并列项目。
- 指标采用官方历史接口中“在对应日桶内创建、采集时仍存在的 Star”。不是两个时点总数相减的净增，也不是从未扣除取消 Star 的新增流水。
- 优先使用现有资源，不新增费用；私人中心、账号收藏等边界保持原约定。

## 2. 本轮实测到了哪一层

| 对象 | 实测结果 | 能支持的结论 |
|---|---|---|
| 全站候选搜索 | 以总 Star ≥15,061 为月榜探索界限，首轮 10 个分片、3,395 个唯一仓库，包含 12 个 fork；第二轮使用新请求重新枚举，ID 集合完全一致 | 本次需核验范围已按搜索接口完成枚举；不是只读 Trending |
| 同窗历史计算 | 3,395 个候选全部成功计分，0 个未解决项；每仓 6 周历史，共用计算三个窗口 | 本批候选的历史数据链路完整 |
| 月榜界限闭合 | 复读入榜项目后，第 20 名 30 日得分为 18,236，高于候选界限 15,061；无第 20 名额外并列 | 在下述索引与采样边界内，月榜 Top 20 实验闭合 |
| 性能 | 历史读取阶段 667.26 秒，约 11.1 分钟；其中 3,256 次现场历史请求、139 个前置样本缓存；一次性使用 4 个读取工作线程 | 是此批次的实测，不是全部产品耗时或下一天的 SLA |
| 中断续跑 | 在 2 个成功分片后主动停止，再续跑；成功分片未重复请求；禁用网络重放得到相同的 2,324 个仓库 | 固定输入下，分片断点恢复有效 |
| 限流与超时 | 隔离注入 429／超时均未写成成功缓存；发现并修复了超时漏记尝试次数的问题，保留首败 | 失败不会伪装成完成；尚未验证真实限流后的自动定时恢复 |
| 条件缓存 | 3 个同日条件请求均返回 304 | 接口支持“未变更则复用”；跨日命中率未知 |
| 连续日更 | 没有连续多个实际统计日的记录，没有真实睡眠后补跑记录 | **尚未验收** |

月榜实验采用固定末桶 (1792281600, 2)，按当前观察映射对应 **2026-10-20**；30 日展示范围为 **9 月 21 日至 10 月 20 日**。这是保守延迟的验证窗口，不是“10 月 22 日最新完整榜单”。

11.1 分钟仅对应历史读取阶段，前面还有种子收集、候选搜索，期间并行做了第二轮新鲜候选核对，结束后复读入榜项目；不能拿这个数字表示整轮实验耗时。研究脚本也没有实现每天换窗运行，不能直接当正式采集服务使用。

独立重算确认：3,395 项最终评分均与保存的历史响应一致；第 21 名为 17,836，与第 20 名相差 400。复读时 3 个入榜项目的历史数值下降，最终榜单已采用新值。研究缓存按接口地址保存，这 20 项的初始原始响应被复读响应替换，初始分数仍保留；最终榜单可以逐桶复算，但不能完整复现这 20 项的初始原始版本。正式历史回看应采用不可变批次存档。

## 3. 为什么只展示 20 名，仍要采集几万个项目

一个项目在某段时间内仍保留的新增 Star，不会超过它当前的总 Star。因此，可以先找到至少 20 个真实项目，得到第 20 名的一个下界，再从全站检查所有总 Star 足以达到该下界的仓库。

这是缩小“可能入榜的全站候选”，不是人为圈定精选池。后续发现更高的第 20 名，界限还能提高。并列项目需要一起保留。

本轮合并了 **3,484 个有效同窗口评分样本**，得到以下容量参考。搜索计数是估计，不是三个范围已经全部枚举：

| 榜单 | 当前样本第 20 名得分 | 探索界限（保留约 2% 余量） | 搜索返回的潜在候选估计 | 全部需重新读取时，按 4,000 次／小时预算折算 |
|---|---:|---:|---:|---:|
| 近 1 日 | 1,034 | 1,013 | 65,946 | 16.49 个小时额度 |
| 近 7 日 | 6,163 | 6,039 | 10,379 | 2.59 个小时额度 |
| 近 30 日 | 18,236 | 17,871 | 2,692 | 0.67 个小时额度 |

月榜本次实际采用的是更宽的初始界限 15,061，所以实际枚举并计算了 3,395 个仓库。它不是表中更紧界限的 2,692 个仓库。

以上数字有四个限制：

1. 这是一个验证窗口的规模，不是每天固定规模，也不是数学上无法再优化的请求下限。继续发现高增长项目可以抬高门槛。
2. “小时额度”不是实际墙钟耗时。运行还受当前剩余额度、重置时点、网络、重试、电脑在线时间影响。
3. 三榜可以共用历史读取，按联合候选计算，不能把三行请求量直接相加。
4. 全量冷启动和每日增量要分开。正确认证且返回 304 的条件请求可免基础额度，但仍需要发请求、耗时并遵守其他限制。跨日缓存命中率未测，不能假定每天都要 16.49 小时，也不能假定缓存会让日更几乎没有成本。

4,000／小时是本次规划预算，给现有账户其他用途留余量，不是 GitHub 官方新额度。约 2% 余量是工程缓冲，不是跨时点数据漂移的数学保证。

## 4. 官方接口带来的真实边界

**搜索不是全站原子快照。** 官方搜索每个查询最多返回 1,000 项，并有搜索范围和超时限制；因此需要细分范围、取齐所有页、核对唯一仓库数和不完整标记。本轮两次候选集合一致增强了可信度，但不能独立证明 GitHub 索引绝对零遗漏，或所有项目共享同一个采样瞬间。[GitHub 搜索规则](https://docs.github.com/en/rest/search/search)

**官方统计日没有完成标记。** 接口返回周起点和周日至周六的日桶，但不保证日界与 UTC 一致，也没有“完整统计到哪一天”的字段。本轮固定较早日桶来验证容量；正式日更应显示真实统计截止桶、采样时间和边界说明，不能把当前未完成日当完整日。取消 Star 也会改变旧日的历史计数。[历史接口](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)、[官方实现说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)

**额度需要分开计算。** 现有个人认证实测基础额度为每小时 5,000 次；认证搜索通常为每分钟 30 次，search 与 core 独立。二级限流仍可能触发，不能把理论上限当推荐持续速度。本轮 4 并发只是有限批次性能实验；正式运行需根据响应节流，并遵守官方请求建议。[REST 限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[最佳实践及条件请求](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## 5. 零新增费用：哪些路线有现实基础

| 路线 | 判断 | 代价或前提 |
|---|---|---|
| 现有 Mac 本地采集 | 当前默认验证路线，无新增云运行费 | 电脑在线时长、初次大批采集、睡眠后补跑都要实际验证 |
| 私有 GitHub 仓库＋托管 Actions | 不适合直接承诺每天数小时仍免费 | 基础套餐免费分钟有限；Free 为每月 2,000 分钟，其他相关套餐可能为 3,000 分钟，且与账户其他用途共享 |
| 公开通用采集层＋私人中心读取成品 | 值得考虑的免费云端候选，尚未选择或实施 | 需要接受公开采集代码和指定公开统计；私人中心、收藏、账户信息不属于拟公开范围；认证、存储及实际调度仍需验证 |

公开仓库的标准 Actions runner 运行分钟免费，但较大型 runner、存储和其他资源不能一概按免费处理。单个托管 job 最长 6 小时；schedule 可能延迟或丢失，不能把登记定时任务当作稳定运行验收。[Actions 计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)、[运行限制](https://docs.github.com/en/actions/reference/limits)、[定时任务规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

另一个关键区别：Actions 默认 GITHUB_TOKEN 通常每仓每小时 1,000 次，不能直接沿用本机 5,000 次的容量。使用独立的云端认证是新的权限配置动作，本轮没有读取或上传本机凭据，也没有借多个账号规避额度。

## 6. AI 日报与每日运行如何接起来

完整链路应是：

固定统计窗口 → 分片找齐候选 → 读取历史并计算 → 核验覆盖与门槛 → 保存榜单快照 → 用现有 Codex 额度生成一次中文日报 → 数字与来源检查 → 页面读取保存的成品。

日报基础是当日成功采集的榜单。未完成的日榜不能被 AI 写成“今日全站完整涨星榜”；可以保留上一份成功榜单并明确截止日期。多人浏览也不应该各触发一次生成。

前轮已实际验证现有 Codex 登录可生成结构化中文摘要，不新增模型 API 调用收费，但消耗现有账户额度。这次没有重复把 5 条样例生成成功升级成完整每日链路已验收。

## 7. 当前判断与唯一下一步

**不需要现在购买服务；也不应现在承诺完整三榜已经能够长期免费日更。** 月榜全候选实验已经闭合，日／周完整候选尚未全量采集。日榜是下一步决定路线的验证对象。

下一步应在隔离环境完成一个 Top 20 日榜的冷启动全批，再用同一采集机制观察至少 3 个真实统计日，记录：候选变化、条件缓存命中率、实际额度与耗时、失败补跑、电脑在线要求，以及何时能够交付日报。跨日记录不能用修改电脑日期或复制同日结果代替。

在这些证据出来之前，保留“免费有技术路径、运行条件待验证”的结论。若本机需要的在线时长不可接受，再决定是否采用公开通用采集层；不要先购买服务器，也不要擅自公开私人中心。

本轮未注册这项连续观察，也没有在后台留下未说明的长期采集任务。
