# 上游搜索缺项：替代查询与补充分片的安全采纳条件

结论：可以研究保持原谓词不变的等价查询，或增加一组互斥且穷尽的子查询恢复同一搜索范围；**不能仅靠某个仓库可以直接读取、两个子查询都返回零，或旧候选清单中没有该仓库，就把 count=1/items=[] 判成完成。** 正常采集应继续，调查证据单独保存，当前榜单仍须所有候选解决后才能完成。

本分析仅只读本地源码、已保存响应和既有覆盖规则；未调用 gh/GitHub API，未修改 live 文件、数据库或进程。查询语法的具体支持情况交由根代理的有限探测/官方文档核验，不把布尔集合推导当作 GitHub 查询解析已验证。

## 1. 当前来源事实

固定坏叶为：`is:public fork:true stars:2051..2051 created:2019-10-05..2019-10-05`。

已保存的 request 430、434、436、438、440 均分别比 reported total 少 1 项。随后按创建日二分，缺项稳定定位到同一天；request 459、460、461、462 均为 total_count=1、items=[]、incomplete_results=false。四次正文哈希相同：`2f016eca5c8ed9b933f09f1a3ccb3143ffef738faf15dfb3a76287865eeb7e6b`。

这支持“计数与列表在上游不一致”，不能区分索引残留、可见性过滤、查询执行差异、时间漂移等根因。HTTP 200 和 incomplete_results=false 本身不足以消除此矛盾。

在截至462的全部已保存成功搜索响应中，没有找到同时满足“2051星且2019-10-05创建”的仓库 ID。已知同日仓库的其他星数样本不能冒充该缺失项。

当前 transport 的投影会丢弃 archived 字段（transport.py 278–279行）；只保留 id、full_name、stargazers_count、fork、private、created_at、updated_at、description、html_url。**因此现有本地响应不能验证 archived 真/假，字段缺失不能解释成false。** 根代理探测 archived 方案时，需要在独立证据中保留 archived 的原始布尔值。

## 2. 原覆盖合同不能改变

当前统计范围是 GitHub 可检索公开仓库，包含 fork；总星阈值和创建日区间切分覆盖相应候选范围。它是不同时间请求组成的非原子索引采样，已承认搜索索引延迟与时间漂移，并非某一瞬间的全 GitHub 快照。

每个叶查询须分页完整、incomplete_results=false、条数与总数一致、唯一 ID 无重复、返回项满足叶谓词；每次枚举所有叶完成后才能进入评分。第二次完整候选枚举和评分缺项门禁仍然保留。

替代方案不能额外排除 fork、archived、低活跃、旧仓库或某种语言，不能以旧排名替代缺项，也不能在查询条件里偷偷加“有 README”“未归档”等方便条件。

## 3. 哪些切分可以成为全集证明

设坏叶的实际目标集合为 P。增加字段切分只有在语义已验证、每个成员必定恰属一个子集时，才能构成 `P=A∪B` 且 `A∩B=∅`。这是集合条件，不是上游服务保证。

| 方案 | 可以采用的前提 | 主要陷阱 |
|---|---|---|
| fork二分 | 根代理已反馈官方规则方向为“移除fork限定词”的原仓分支 + fork:only分支；仍需保存规则来源与探测证据。完整保留public/stars/created条件，返回fork必须为布尔且与分支一致 | fork:true在当前模型里表示包含fork，不能把fork:true和fork:only当成两个互斥分支；不要叠加两个fork限定词并猜解析优先级；未核验的fork:false不能仅因看起来像布尔语法就采用 |
| archived二分 | archived:true与archived:false准确语义已核验；两个分支均保留fork:true与原限定词；返回archived必须完整保存并逐项验证 | 当前缓存没有archived字段；只查询false将缩小范围；归档状态可变，跨请求可能迁移 |
| 等价写法/排序/分页大小 | 目标谓词确实等价，仅改变执行形状；完整获取所有分页并验证ID、条数和谓词 | 关键词“类似”不代表语义等价；改排序后只取首页不是完整；查询字符串不同不能自动充当相互独立证据 |
| 按owner/name猜测二分 | 不推荐作为本次修复 | 名称字符域、大小写、Unicode、转移/改名及漏分支难以证明穷尽；扩大实现复杂度 |

以上两种布尔二分在一个固定状态中可以穷尽。实际连续请求并非原子快照：fork状态/归档状态/公开性/总星可能变化，同一ID可能重复或漏过。跨分支出现重复时不能直接去重后宣称完整；须保留漂移证据，重查受影响组，并用原有第二轮枚举处理整批变化。

## 4. 本次最小采纳门槛

必须同时满足以下条件，才可讨论把替代结果用于关闭这个未解决叶：

1. **范围有证明。** 明确记录原叶P、每个子查询的确切完整字符串、字段语义证据和穷尽/互斥关系；或记录等价查询的等价理由。
2. **响应可审计。** 保存请求时间、endpoint、HTTP状态、total_count、incomplete_results、完整分页ID及所需谓词字段、正文哈希。来源须是真实读取，不能手工造响应或复用旧时间戳。
3. **每个子查询自身完整。** 未超过分页上限，所有页条数闭合，没有缺页、重复或未知；私有/时间/星数/fork/archive谓词逐项校验。任一分支仍count/list不符，则该组仍unresolved。
4. **组间一致。** 合并ID唯一且满足原叶；在接近时间的复核中，总数与原叶/子查询合计可解释地闭合。已知原叶持续报1时，子查询合计0不能被视为成功；若合计与原叶不等，也不能挑一个“看起来可信”的计数放行。
5. **有限新鲜复核。** 在补充结果后复核同一组，ID集合、计数和关键谓词稳定；若原叶依旧items为空，但等价组每次都完整给出同一ID，才有依据把该组视为原叶的可重复替代采集路径，并保留原矛盾标签。这仍仅满足已有非原子索引口径。
6. **后续链路完整。** 补出候选须进入原评分、第二次枚举及最终验证；不能因补出某个ID便提前解除整批完成门禁。未知评分不补零，末位并列保持。
7. **账本一致。** 新查询的请求、分支定义、父子关系、页及成员来源在独立候选设计中明确；最终可从保存响应重放得到同一成员集合。完成状态的变更与成员检查点必须原子提交。

若原叶count=1、两个完整子查询分别0和1，唯一返回项满足全部原谓词，后续重复读回稳定，这是最清晰的可采用证据。若0和0，说明矛盾仍存在；“大概是幽灵仓库”只是待验证假设。

若原叶计数确已新鲜变为0且完整返回空，可以按同口径处理当前采样变化；必须保留先前count=1异常以及变更时间，不能改写历史。前后计数不同本身不证明缺项已经被识别或原先确实无仓库。

## 5. 直接读取仓库能证明什么

直接GET仓库可以验证某ID在该读取时点的存在性、公开性、创建日期、总星及相应字段。按ID验证可避免改名造成误对齐，也可辅助发现搜索索引与详情的不同步。

但直接读取不能单独证明：该仓库仍属于当前搜索索引、它就是那一个未返回的成员、没有另一缺项，或原叶已全部枚举。即使它恰好满足2051星和创建日，也只是一个合格候选，不是count/list完整性证明。读取失败也不能自动解释成不存在或0分。

因此，直接读取仅作为候选验证或上游异常诊断证据；必须与上面的等价范围枚举闭合证据组合，才能用于恢复。若仓库已变私有/删除/受限，保持公开读取权限边界，不尝试绕过权限或把未知当成成功排除。

## 6. 实现与运行风险

现有 shard key 只有 `[lo,hi,cl,ch]`，members/pages以此关联，无法区分同星数/日期下的fork或archived子分片。只在请求字符串加过滤而不扩展分片身份，会引起覆盖碰撞、错误复用或遗漏分支。实现前须在隔离候选中定义新身份与兼容迁移；不应手工往当前活跃DB补members或把父叶改complete。

现有修复计数使用事件按job/pass/shard键持久化；新增子分片或等价读取需明确重试上限与父叶未解决状态，不能靠“换个查询字符串”无限重置失败次数。

调查阶段保持正常采集不断；根代理若最后决定采用修复，也应先完成离线复现与安全审查，再在符合已授权运行边界的时机切换。调查本身不授权扩大费用、配额、目标日、总截止或降低完整性。
