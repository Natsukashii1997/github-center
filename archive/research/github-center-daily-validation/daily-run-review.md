# 全站涨星榜：每日运行与完整性独立审查

核验日：2026-10-22。只读审查前轮证据与 4 个 GitHub 官方文档页面；未发起采集、读取凭据、安装、注册自动化或付费。用户已批准近 1／7／30 个官方统计日、每天更新。旧报告中的“尚未批准”已过时。

**结论：免费额度可以支持一定规模的每日全站候选核验，但现有证据不能证明三榜完整采集能在一天内稳定完成，更不能证明严格同时点全站零遗漏。必须分别验收覆盖、耗时、恢复和连续运行。**

## 1. 官方限额：需要修正和保留的事实

| 项目 | 官方依据与对方案的影响 |
|---|---|
| 基础读取 | 个人认证通常为 5,000 次／小时，同一用户的个人令牌、代表用户调用的应用共享相关额度；不是每换一个令牌就另得一份。 |
| 搜索读取 | `search` 和 `core` 是分开的资源桶。认证仓库搜索是 30 次／分钟。搜索分页数量应单列，不能又全部计入 core 的 5,000 次。 |
| 搜索范围 | 每个查询最多返回 1,000 条。文档还列出检索范围限制；宽查询适合发现规模，不构成全站完整导出合同。需要进一步分片。 |
| 二级限流 | 同时最多 100 个请求、REST 通常最多 900 点／分钟，以及 CPU／计算负载等限制；这些上限不是应主动跑满的目标。规则可能变化，部分未公开。 |
| 计数依据 | 每个响应的 `x-ratelimit-*` 是实时节奏依据，优先于 `/rate_limit` 概览；跨区域响应的 remaining 未必单调递减。 |

依据：[REST 限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[独立资源桶](https://docs.github.com/en/rest/rate-limit/rate-limit)、[搜索限制](https://docs.github.com/en/rest/search/search)。

官方建议排队串行请求。收到限流后，有 `Retry-After` 就等待指定时间；remaining 为 0 就等 reset；其他二级限流至少等一分钟，再有限次指数退避。不能重试到成功为止。正确认证的条件读取若返回 304，不消耗 primary 额度，但是否支持、命中率多高，需要实测。[官方最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

## 2. 动态候选界限数学成立，但有适用边界

令 `G(r,w)` 为仓库 r 在固定统计窗口 w 内产生且读取时仍存续的 Star，`S(r)` 为其当前总 Star。同一事实时点下，`G(r,w) ≤ S(r)`。

若至少 N 个已核验项目的窗口得分不低于 B，则其余 `S < B` 的项目不能进入这个 Top N。为了保留末位并列，必须继续覆盖 `S = B`。三个窗口可共用一次足够长的历史读取；联合候选界限取三个有效界限中的最小值，各榜分别判断是否完成。

这是全站筛选算法，不是精选项目池。但以下条件缺一不可：

1. 窗口在运行开始时固定，所有仓库用完全相同的日桶集合；不能把最近 7 个统计日换成上个自然周。
2. 搜索包含全部公开仓库及 fork；分片覆盖整个需检查的总星区间，叶片不超过 1,000 条，并核对全部页、唯一仓库数和响应完整状态。密集同星值还需二次分片。
3. 任何未知历史、分页失败、未完成分片都不能当作 0 分或已覆盖。仓库消失、改名、转私有等需保留处理结果。
4. 动态提高阈值前，要有足够的实际分数支持。最后需重新核验当前末位分数仍支撑所有曾经丢弃的范围；若不成立，恢复这些范围。

**非原子性无法被上述算式消除。** 搜索和历史在不同时间读取，仓库可在搜索分片之间移动，历史存续数也会下降。无重叠数值分片只在静态数据上严格互斥完备；实时数据还需边界复读、去重和差异核对，且仍不等于上游提供了统一快照。`incomplete_results=false` 只是接口未报告该次超时不完整，不能证明索引绝对零遗漏。固定一个“安全余量”只能缓解，不能数学保证。

前轮 Top 1 实验已经出现种子 232,274、复读 232,273 的真实回撤，之后扩到 230,000 并复读才通过预设条件。这是必须保留最终界限复核的直接证据；不代表后来三个周期的大榜已验证。

## 3. 免费每日运行的容量判断

容量应按实测变量判断，不能只用“有 5,000 次额度”下结论：

- `C`：三窗口联合候选中实际需读取的不同仓库数。
- `R`：失败、边界、历史异常、最终界限等额外 core 读取数。
- `A`：留给本任务的每小时 core 预算，必须为用户其他工具留余量。
- `L`：真实请求延迟；`H`：电脑当天实际可运行的小时数。

保守容量判断为 `(C + R) / A ≤ H`，同时检查串行耗时、搜索节奏、退避和日报生成是否赶得上交付时间。这个式子是规划近似，不能代替真实跨重置窗口运行。

例如以 **假设** A=4,000／小时为本任务预算，前轮 14,767 个候选约需 3.69 个小时额度；若联合候选有 100,000 个，则约需 25 个小时额度，已不适合单日满量更新。两者都未计失败与等待，不是实际耗时预测。动态界限可能缩小候选，但需用最终数据证明。

不应把三个榜的候选量直接相加；一次历史数据能支持三个窗口时，应按联合集合计量。也不能预先假设条件请求会把每日费用或额度压低到近零：需要记录实际 304 比例和仍消耗的请求。

## 4. 基准路径、不利情景与发布门禁

**基准路径：**电脑当天在线足够长，GitHub 认证有效，联合候选量在预留预算内；固定统计窗口 → 分片枚举 → 排队采集／断点保存 → 三榜独立验收 → 保存不可变榜单快照 → 生成并核验一次 AI 日报 → 切换当天成品。

**不利情景：**电脑睡眠／断网、其他工具消耗额度、接口限流、候选骤增或边界回撤。应保存未完成工作并延后补跑，页面显示真实采集截止日和更新状态。不能把旧榜改日期当新榜，不能让缺数据的榜触发“全站完整日报”。恢复时沿用同一运行窗口，不能把今天取到的部分与明天的新窗口混成一榜。

运行中断后，应只重试未完成单元；同一日同一窗口重复启动不产生两份正式榜和两次 AI 消耗。一次完整运行与故障恢复可以当场验证；跨日无人值守、睡眠后补跑、长期免费额度是否够用，必须经过真实多日观察，不能用改日期模拟代替。

建议首阶段验收线：

| 验收对象 | 可接受证据 |
|---|---|
| 完整候选采集 | 分片清单、范围覆盖、页数／唯一仓库数、全部失败状态、最终阈值复核；三榜分别给通过或未完成 |
| 实际容量 | 一次全批开始／结束时间、真实 core/search 请求数、等待和重试、其他任务余量；据此估计当天可运行时间 |
| 中断恢复 | 人为中断隔离运行后恢复，已成功单元不重复请求，无遗失记录，最终结果与不中断对照一致 |
| 同日幂等 | 重复执行不重复发布／生成日报，原始快照不被悄悄覆盖 |
| 限流恢复 | 用隔离故障响应验证等待与退出，不以主动耗尽真实额度作测试 |
| 每日采用 | 至少数个真实统计日记录，包含一次自然离线后补跑；再判定是否满足个人日常使用 |

目前可确认的是已有认证与小规模数据链路；不能宣称完整 Top 20／100 的三榜、最新完整统计日标识、每日无人值守、严格同时点全站快照已经验证。

## 6. 当前隔离采样器实现审查

新增只读检查对象：同目录 `collect_probe.py`。检查时程序仍在运行；未修改程序、读取凭据或打断运行。以下仅判断它能支持哪些研究结论。

### 已经合理的部分

- 日桶固定为 `week=1792281600, day_index=2`。1／7／30 日逐日向前枚举，跨周的整除与余数正确，6 周历史足够覆盖此次 30 日范围。没有用最后非零值猜测截止日，也没有把近 7 日替换成前一整周。代码明确该桶不是“最新完整统计日”的证明。
- 检查一周恰有 7 个非负整数，日和等于周总数，周不重复；缺少应有周时失败，不直接填 0。对确定早于创建的缺失整周采用保守补零规则；这个规则可能多报缺失，但不会因为所有缺失一律补零而制造虚假低分。
- 公开范围与 fork 显式包含；搜索的不完整结果仅用于种子探索。逐项结果采用临时文件替换、HTTP 成功响应留缓存，有助于中断后复用已经取得的证据。
- 结果文案明确“sample / NOT global”。失败并未变成 0 分。当前功能适合做种子规模调查，不足以宣布完整榜。

### 会影响结论的具体限制

| 级别 | 位置／问题 | 研究结论应如何处理 |
|---|---|---|
| 重要 | `survey()`、`summarize()`：只读种子历史，随后请求阈值查询的第一页计数；没有分片／全页枚举／全候选评分 | 输出只支持初始界限和规模线索；不得称“全站三榜已采完”。样本 Top 20 只能标为样本排名。 |
| 重要 | `summarize()`：当第 N 名得分为 0 时，`max(1, floor(cutoff*.98))` 丢弃总星 0 的并列者 | 此情形只可报告“没有得到正的有效剪枝界限”；不能据此证明包含全部末位并列的榜单。若当前所有目标 N 的截断分数均为正，这一边缘项不影响本次规模估计。 |
| 重要 | `api()` 与 `survey()`：缓存键只有 endpoint；`scored.json` 中已有仓库直接跳过 | 对本次固定窗口继续跑有效；改截止桶或隔天重用目录会读取旧历史／旧分数，不能称已实现每日更新或跨日恢复。历史值会随取消 Star 回撤，也需区分本次冻结证据与刷新读取。 |
| 重要 | `api()`：额度保护在请求成功后检查，异常时直接退出，没有真正等待 reset／Retry-After 的恢复调度 | 属于“停止并保留断点”，不是“限流后自动恢复已跑通”。已缓存响应恢复读取不会再次检查实时额度；不应靠反复启动消耗剩余保留额度。 |
| 重要 | `api()`：90 秒超时抛出发生在请求日志记录之前；`network_count` 也在返回后才加 | 容量统计必须把超时尝试补计，不能仅按 requests.jsonl 行数称所有真实请求数。该次请求可能已到达服务器，费用／额度状态是未知，不是 0。 |
| 建议 | 成功重试后不从 `history-failures.json` 清理旧失败 | 正式汇总应区分历史失败与当前未解决失败；不能把旧失败数量当作当前阻塞数量，也不能因为失败字典存在就否定已经成功的补读。 |

读取运行中间态时，已有 83 个评分记录、1 个缺少所需周的失败，结束汇总文件尚未生成。这仅说明该时点的进展，不是最终规模或最终失败数；缺周原因应在最终汇总前定点核查，不能为了消除报错直接补 0。

### 容量采样的呈现规则

这份采样可提供实际响应延迟、采样耗时、成功／失败数和初始候选计数，但不能直接把种子样本的响应延迟外推成全批 SLA。种子混合了热门与总星较高项目，且短批未经历跨小时额度重置、长时限流和离线。计时需分开请求自身耗时、搜索节流、重试／等待、整体开始结束；API 与两个 Trending 页面读取分开计数。

阈值 count 是探索估计，特别是 `incomplete_results=true` 时不能作为完整分母。即使为 false，也没有完成分页覆盖证明。动态剪枝可能改变最终候选量，因此用当前种子界限推算的工作量应标为“按当前探索界限的情景”，不是不可降低的最低成本。
