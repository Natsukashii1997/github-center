## 上界论证及适用条件

若某仓库在固定窗口创建且当前仍有效的 Star 数为 G，其同一时刻总有效 Star 数为 S，则 G ≤ S。已完整枚举 S ≥ L 的所有公开仓库，并成功得到它们的固定窗口分数后，只要第 20 名门槛 C ≥ L，未枚举仓库满足 G ≤ S < L ≤ C，不可能进入榜单或成为末位并列。

本轮 L=15061；代码的 `cutoff >= manifest.low` 方向正确。**但这个数学论证要求总星筛选与分数对应同一口径、相容时点且搜索可完整枚举。GitHub Search 的索引、缓存和非原子多页读取没有自动满足这些前提。** 2% 探索余量可以降低边界漂移概率，不能成为数学保证。

## 重要发现

### 重要：完成候选读取不等于绝对全站完整

位置：`enumerate_probe.py:40`、`month_batch_probe.py:56`。

分片内总数一致、无重复仍不能排除读取期间等量成员替换或索引滞后。不同分片也在不同时间完成。最终 `candidate_histories_complete=true` 最多证明这份候选清单的读取完成；代码已保留 `global_absolute_completeness_claim=false`，这是正确边界。

结束复读仅针对 Top 20，不能发现初次枚举未纳入、随后跨过总星门槛的仓库。至少要进行新鲜的候选/边界枚举核对并补读新 ID，或保持“在本轮 GitHub 搜索索引候选范围内完成”的条件性结论。即使两轮 ID 一致，也只是稳定性证据，不能将 Search 升格成全球原子快照。

### 重要：断点与缓存尚未绑定日更批次

位置：`month_batch_probe.py:16`、`collect_probe.py:55`、`enumerate_probe.py:17`。

结果文件只按仓库 ID 判断已完成；历史缓存只按 endpoint 识别；枚举叶节点存在即跳过。它们没有绑定窗口、算法版本、枚举清单签名或过期时间。当前同一固定窗口的一次性研究可进行证据复核，但次日直接复用目录会跳过重新计分或重新采集，不能由本次推断“每日自动更新已跑通”。

应在未来日更执行前将批次日期/窗口、算法版本和源响应时间显式写入独立批次，并区分同批次恢复与新一天刷新。本审查不改源码。

### 重要：日界和非原子采集仍是显式假设

位置：`collect_probe.py:133`。

按 604800 秒倒推周键及周内下标，是当前 API 样本的固定映射。官方不保证 UTC 日、周边界，不能据此认证最新已完成日。当前选择延迟的周二作为容量/恢复验证窗口是合理的；完整性结论仍须附该窗口假设。逐仓库响应也并非统一时刻，旧日 Star 会因取消而变化。历史快照需保留采集时段与实际版本。

### 建议：额外检查总星上界反例和身份

本轮结束应逐项比较 `score30 <= search_total_stars`。若出现反例，意味着时间、缓存或数据口径前提已失效，不能只靠截止值大于阈值宣称通过；无反例也不证明未观察仓库满足同样条件。

仓库 ID 来自搜索，history 按 full_name 读取。长批次里重命名、重定向或名称被重新占用可能造成身份歧义；最终入榜仓库复读元数据时应确认 ID 与清单一致。错误文件与随后成功文件可同时残留，最终应以当前批次成功证据及未解决清单为准。
