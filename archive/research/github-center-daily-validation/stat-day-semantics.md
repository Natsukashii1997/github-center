# GitHub 官方日桶语义核验

核验时间：2026-10-22。范围：官方文档、官方工程说明、官方社区答复，以及一次当前公开仓库响应；未读取凭据、修改配置或安装依赖。

## 结论

可以按 GitHub 返回的日桶做固定的近 1 / 7 / 30 桶排名，但现有合同不足以证明“最新已结束的统计日”及其准确 UTC 截止时刻。当前实测与 UTC 日历对齐，只能作为运行假设，不能升级成官方保证。完整自然周不是最新 7 日的替代品。

## 官方已明确的内容

来源：[Starring REST API](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)。本轮额外读取该页内嵌响应 schema，确认：

- `week` 是该周开始的 Unix 时间戳，单位按标准 Unix 秒解释；不是采集时间，也不是该周累计值的测量时刻。
- `days[0]` 到 `days[6]` 分别是星期日到星期六的新增 Star 计数；`total` 是该周计数。
- 日、周边界不保证与 UTC 对齐。不能将 `week + i × 86400` 直接声称为官方逐日时间戳；夏令时等日历边界也未获合同解释。
- 页内按新到旧返回，分页向仓库创建周回溯，零 Star 周仍保留。
- 响应 schema 只有 `week / total / days`，没有时区、逐日时间戳、当前日索引、已完成日标记或统一快照时刻。

[官方工程说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)说明按请求参数先限定 `created_at` 周范围再聚合；未补充每日完成标记或时区保证。[官方社区答复](https://github.com/orgs/community/discussions/206104)确认其统计的是对应日期创建且现在仍存在的 Star；取消 Star 会改变旧日计数。因此日桶结束与历史计数永不变化是两个不同问题。

## 当前小样本

公开只读请求：`GET /repos/star-history/star-history/stargazers/history?per_page=5&page=1`。

HTTP `Date`：`Thu, 22 Oct 2026 10:02:43 GMT`；响应选择版本：`2022-11-28`。

| week | 转为 UTC 的周起点表示 | total | days（周日到周六） |
|---|---|---:|---|
| 1792281600 | 2026-10-18 00:00Z | 26 | 7, 6, 4, 7, 2, 0, 0 |
| 1791676800 | 2026-10-11 00:00Z | 38 | 6, 5, 3, 9, 9, 3, 3 |
| 1791072000 | 2026-10-04 00:00Z | 30 | 1, 4, 4, 4, 4, 6, 7 |
| 1790467200 | 2026-09-27 00:00Z | 23 | 2, 5, 2, 6, 2, 5, 1 |
| 1789862400 | 2026-09-20 00:00Z | 26 | 3, 1, 3, 6, 7, 3, 3 |

这个样本与“周四正在进行、周五六尚未开始”相容，但零也可能是一个真实无 Star 日，不能从末个非零项推出当前日。HTTP Date 只能证明服务响应时间，不能证明日桶时区或结算状态。

按目前观察到的 UTC 映射，固定末桶为 `(1792281600, 3)`（标签 10 月 21 日，周三）：近 1 桶为 7；近 7 桶为 39；近 30 桶为 137。上一完整自然周为 38，日期范围不同，不能替代近 7 桶。

## 建议的可实现规则

1. 每次批次开始只确定一次窗口，并写入清单：参考响应 Date、末桶 `(week, day_index)`、所需 1 / 7 / 30 个桶键、映射假设、采集开始结束时间。全站候选使用同一套键；不能每读一个仓库都重新按当前时间选窗。
2. 内部真实主键保留 `(week, day_index)`；UTC 换算日期只是展示标签。当前研究运行可采用已观察的 UTC 映射排除当日，但 `completed_day_verified=false`、`boundary_mode=observed_utc_mapping` 必须保留。
3. 每仓库至少请求最近 **6 周**。周日执行时最新周不能贡献完整日，余下 4 周只有 28 天；请求 5 周不足以覆盖所有运行日的近 30 天。跨周逐桶拼接，完整保留 0。
4. 验证桶数量、非负整数、周总和、重复/缺失周、候选间周起点一致性。边界模式变化、响应缺周或不足以覆盖窗口时，不发布“完整榜单”，保留上一成功批次并标记本次未完成。
5. 即使窗口固定，仓库依次查询也不是一个原子快照；保留采集时段，旧桶数值变化允许形成新版本，历史榜单保留当时发布值。

## 产品可诚实使用的说明

研究阶段可展示：**“近 7 个 GitHub 统计日桶 · 截至 10 月 21 日（日期按 API 周起点换算）”**。说明：**“每天采集一次；日桶边界以 GitHub 返回为准，不承诺北京时间或 UTC 自然日。统计为这些日桶内创建且采集时仍有效的 Star。”**

当前不能标记为“最新完整自然日已验证”或“实时精确净增”。要升级成精确、已结束日合同，需要 GitHub 明确时区/日边界规则，或返回逐日边界及完成截止字段。跨日观察可以提高实践信心，却不能代替这一长期保证；两个观察值相同也不代表日桶已结束。

下一步不需用户判断 API 技术细节：按以上显式假设跑通采集、同窗排名与每日恢复验证；将时间边界列为已识别的接口限制，与候选覆盖完整性分开报告。

## 本次容量与恢复验证的保守窗口

建议固定末桶 `(1792281600, 2)`，即当前观察映射下的 2026-10-20 周二。相对通常选择的前一日再延迟一天，可避开临近日界的变化，用于采集规模、排名覆盖和断点恢复验证；这不是“最新完整日已证明”。同一仓库样本对应近 1 / 7 / 30 桶为 4 / 41 / 131。

不能混淆“桶起点已过去 48 小时”和“桶结束后已过去 48 小时”。本次响应时间距离周二假定起点约 58 小时，距离假定结束仅约 34 小时。若工程合同写“结束后至少 48 小时”，本次应选择周一 `(1792281600, 1)`。两种保守延迟都必须显式承认日边界映射假设，不能当作 GitHub 官方完成标记。
