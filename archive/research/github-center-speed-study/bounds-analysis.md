# 全站日榜无损剪枝与每日候选提速研究

研究日期：2026-10-22。只读检查现有程序和已保存样本，未停止/重启/修改当前采集，未调用认证 GitHub API；新增内容仅在本研究目录。本报告是算法可行性分析，不是已部署提速结果。

**结论：可以减少多余候选和搜索探测，但现有可靠证据不支持把全站日榜从约 6.6 万次冷历史读取直接降到只读几十个项目。最稳妥的提速是先读少量同窗口种子，尽早建立有证据的入榜门槛，再用总 Star 上界剪枝；这保留全站范围，但不是独立于当天数据的数量级加速。**

## 1. 成立的界限与完成条件

GitHub 当前星数表示仍在 Star 该仓库的用户数量；历史接口按创建日聚合当前记录。源码机制解释见 [官方工程说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)，接口字段与日桶说明见 [官方 Starring 文档](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)。

以下是基于该计数语义的数学推导，而非 GitHub 另行承诺的排名服务。令某仓库当前总 Star 为 S、目标日的存续新增 Star 为 D，则同一状态下 0 ≤ D ≤ S。如果已经新鲜取得 20 个不同仓库的目标日分数，最小者为 L，则全站第 20 名不低于 L。于是 S < L 的仓库不可能入榜；S = L 不能排除，因为用户要求保留末位并列。

例：已确认 20 个项目当天都至少新增 1,000 个存续 Star，某仓库当前总星只有 700，数学上不可能入榜。全站范围仍由公开索引搜索覆盖，只是可以证明无缘入榜的部分不读历史。

执行要求：种子必须读取本次目标日，不能直接用昨天排名分数；全站查询保留 `is:public fork:true`，无语言/主题限制。完成时新鲜复核排名门槛，如果掉到已排除范围以下，必须补采被排除区间。任何尚不能证明上界的候选仍读历史；未知/错误不能补零。GitHub 搜索与历史读取非原子、索引有时间差，仍保留当前方案已经声明的“索引覆盖、分批采样”边界，不能升级为同一瞬间的绝对全站快照。

[官方搜索文档](https://docs.github.com/en/rest/search/search#search-repositories)限制每查询最多 1,000 条，因此全站分片与分页不能省掉。[仓库搜索规则](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)明确了总星区间、公开性及 fork 的范围条件。

## 2. 最值得做的三个优化

|顺序|做法|为何不缩范围|收益边界|
|---|---|---|---|
|P0|先刷新昨天榜单、近几日临界项目等几十到几百个种子，按今天窗口建立 L；再开始大规模候选枚举与历史读取|种子只提供门槛，不定义最终候选池；门槛外仍由总星上界证明排除|避免现程序直接按“昨天门槛×80%”扩大今日候选；实际收益取决于当天门槛|
|P0|按当前总星上界从高到低处理；新鲜同窗口第 20 名升高时更新下界；下界下降时恢复被排除范围|所有未读区间都有记录的上界，只有严格低于最终门槛才能结束|如果当前 1,013 下界已接近真正日榜门槛，提升可能有限|
|P1|复用昨天已验证的分片边界，今天仍新鲜枚举每片，超容片继续拆分，区间并集保持完整|复用的是切分方案，不是昨天的成员清单|减少重复父节点搜索和空范围探测；不能消掉逐仓历史请求这个主要成本|

目前程序的初始流程是“枚举全部候选→读取全部历史→再枚举→复核”。下一日初始门槛取上一日第 20 名×80%；仅当最后门槛低于起始门槛时向下扩围，没有在全量读取中途根据已确认当日门槛向上收缩。因此上述优化确有实现空间，但本轮保持冻结程序不动。

## 3. 已有样本量化：收益存在，当前冷启动已经用过一部分

读取 `data/scored.json`、`month-final-scores.json`，按固定 2026-10-20 日桶合并复算：

|已保存样本|样本内第 20 名|带 2%余量的探索下界|此前搜索估计的候选数|
|---|---:|---:|---:|
|228 个种子|956|936|70,832|
|3,484 个合并样本|1,034|1,013|65,946|

同窗口更好的种子把候选估计减少 4,886 个，即 6.90%，对应约 1.22 个“每小时 4,000 次”额度。**当前冷启动已经采用 1,013 下界，不能把这份收益再计为未来新增提速。** 1,013 提高到 1,034 后的实际候选数未测，不能把门槛提高 2%说成请求减少 2%，更不能承诺减少十倍。此处所有候选数都是已保存搜索估计，并非已完成日榜的最终全量分母。

只看 3,395 个高总星月榜候选，样本内日榜第 20 名反而只有 818；合并小仓库热点样本才得到 1,034。这说明种子可以优化读取顺序，但不能以高总星池或昨天 Top 20 代替全站搜索。

离线计算的紧凑证据见 bounds-offline-evidence.json。

## 4. 不能当成无损优化的捷径

**“总 Star 没变就跳过”不成立。** 昨天 1,000 星，今天新增 500、取消 500，今天仍是 1,000；目标日存续新增可以有 500。总量相等不意味着日桶相同。即使总量下降，也可能同时有大量新增与更多取消。

**“昨天未上榜，今天就不读”不成立。** 热点可能突然发生，昨天分数不是今天分数的上界；只跟旧清单会漏掉新进候选。`pushed` 反映提交更新，也不是 Star 变更游标，不能仅取最近 push 的项目。

**“昨天读过的未来目标日桶可作永不增大的上界”目前不能作为严格默认。** 当前 6 周响应确实包含后续要排名的其他日桶，这是很有价值的预取。机制上，已经彻底结束且不再补写的创建日记录只会随取消 Star 减少；若有这项保证，旧桶 < 当日门槛即可跳过，理论节省非常大。但官方文档明确周/日边界不保证与 UTC 对齐，也没有已完成日水位、延迟补写上界或“历史桶单调不增”的服务合同。工程博客支持记录删除与创建时间聚合的机制推论，不能据此声称完整性已被证明。当前产品要求零额外覆盖损失，因此先将该路线保留为待核验假设；只有官方明示保证，或用户接受额外的数据修正风险，才可升级为主剪枝依据。短期样本从未见上涨也不构成全站保证。

**“过了第一轮就省掉新鲜全站复核”会削弱现有非原子采样防线。** 可以优化复核的分片方案，但没有可靠全站变更流前，不能只刷新旧名单并把结果说成同等覆盖。

## 5. 顺带避免未来 1/7/30 日榜重复读取

当前一条历史响应带 6 周，足够覆盖同一结束点的 1/7/30 日窗口。以后应在同一响应上计算三个分数，并对三榜候选做并集后只取一次历史；不为三个页面分别采三遍。这是确定可行的请求复用。若各榜起始门槛不同，候选范围用门槛的最小值或等价并集，不能假定所有时候周/月榜候选一定已被日榜包含。这主要避免未来功能叠加的额外成本，并不是本次单日采集还能再省三分之二。

## 建议验收

当前冷启动继续作为完整基线。结束后对同一组不可变输入离线重放“现有固定下界”和“种子优先+动态上界”，比较相同 Top 20 含并列、排除证书、跌破门槛补采、请求需求数；再用后续固定统计日真实运行比较。只有同窗、同覆盖、同最终榜单的证据才能报提速比例。种子、历史上界或分片失败时回到全量路径，不把失败降级为近似榜。
