# 日榜每日容量与传输提速审查

审查日期：2026-10-22。仅只读当前代码、以 SQLite `mode=ro` 查询运行状态，并查阅公开官方文档；未发认证 API 请求，未停止或重启工作进程，未修改采集目录的代码、配置或数据库。本文件位于独立研究目录。

## 结论

在约 6.6 万候选、不发生额外扩围的假设下，当前冷启动约 18–22 小时可勉强装入 24 小时，但不够据此承诺每天稳定更新。后续真实 304 确实能降低核心额度消耗；然而仍要联网验证每个候选，因此即缓存非常好也不会变成分钟级。若有效 304 比例达到 50%–75%，当前调度参数的规划模型约为 6.6–10.2 小时；这不是实测结果。

优先做“减少必读候选 + 稳定条件缓存 + 复用搜索分区边界”。不要优先增加并发、创建多 Token、挤占用户预留额度，或跳过当天全站候选检查。当前运行保持不变，先取得完整对照。

## 已核对的当前事实

2026-10-22 20:05 北京时间快照：冷启动仍处于初次候选枚举；已保存 20,903 个唯一候选。264 次搜索成功，平均响应 4.46 秒；最近 5 分钟为 57 次成功搜索、平均约 5.05 秒。没有核心历史请求，因此本轮历史读取速度和跨日 304 命中率仍未知。

代码配置：四个读取工作线程；全局请求启动间隔至少 0.25 秒；搜索至少间隔 3.1 秒且当前按顺序执行；核心请求采用每滚动小时至多 4,000 个非 304 请求的本地预算，并结合服务端剩余额度保留约 1,000。每次网络请求启动一个 `gh api` 子进程。

当前阶段顺序为：初次全量搜索 → 所有候选历史读取 → 第二次全量搜索 → 新加入候选补读 → 入榜临界复核。两轮搜索并非重复错误：第二轮承担长时间读取后的候选变化检查。当前第二轮也从根查询重新分片，尚未复用第一轮边界。

后续批次候选起点是前一批最终第 20 名的 80%。例如若第 20 名约 1,034，下一批门槛约 827，比本轮 1,013 更低；候选可能明显增加。当前代码只在门槛不够低时扩大范围，不会因为新窗口实际第 20 名较高而主动收紧。因此不能默认之后每天恰好仍有 65,946 个候选。

## 免费条件缓存能解决什么

GitHub 官方确认：正确认证的条件请求若返回 304，不消耗主要额度；响应内容较小、查询参数稳定有助命中。304 仍然是一次真实请求，仍有网络、调度及其他限制成本；未请求就直接使用旧文件不算今日校验。[官方最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

当前实现已保存 ETag、不可变正文及每次校验记录，后续日批会发条件请求。没有必要再把“接入缓存”当成一项尚未实施的大提速：现在缺的是跨日命中率实证。`gh api --cache` 的本地时长缓存不能替代这些每日真实校验。[GitHub CLI API 手册](https://cli.github.com/manual/gh_api)

统计分母必须正确：设已缓存候选比例为 q，其中条件请求返回 304 的比例为 p，则全部历史请求的有效 304 比例 h = q × p。例如当天 80% 仓库已有缓存，条件命中率 75%，有效命中只有 60%；新进入候选范围的仓库仍需 200。不要将“缓存库内命中率”直接套在全部候选上。

日榜当前读取六周：其他日期新增 Star、取消 Star、周边界使周列表前移，都可能改变整个响应，哪怕目标日桶的数值不变。官方端点返回最近周在前、包含零值周，且没有承诺 UTC 边界。因此周切换可能让许多不活跃仓库也重新返回 200。这个风险是按响应结构作出的推断，不是已测得的具体失效率；周中三日高命中不能证明每一天都高命中。[Star history 官方定义](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)

## 情景模型，不是测速结果

假设候选 N=65,946；核心预算 B=4,000 次/小时；请求启动间隔 d=0.25 秒；四个线程；两轮搜索合计 S≈2 小时。前轮另外一次验证的 3,508 次历史 200 平均耗时 0.824 秒、中位数 0.758 秒，尚不是本轮实测。

粗略规划式：`T ≈ S + max(N × d / 3600, N × 单次延迟 / 4 / 3600, N × (1-h) / B)`。

它忽略失败重试、页面漂移、局部预算等待、入榜复核、共享额度占用和电脑睡眠，只用于说明决定量级的因素；滚动预算初始突发和请求分布也会使实耗偏离。表格不能作为 SLA 或验收值。

|全部历史请求中的真实有效 304 比例 h|约需占用主要额度的请求|额度量级|含约 2 小时搜索的理想调度量级|
|---:|---:|---:|---:|
|0%|65,946|16.49 小时|18.49 小时|
|25%|49,460|12.36 小时|14.36 小时|
|50%|32,973|8.24 小时|10.24 小时|
|75%|16,486|4.12 小时|6.58 小时|
|90%|6,595|1.65 小时|6.58 小时|

75% 到 90% 没继续明显降低模型耗时，是因为 65,946 次请求按每 0.25 秒启动一次已经需要约 4.58 小时，加上搜索约 2 小时。这个 4.58 小时是当前参数的调度下界，不是 GitHub 保证能够达到的速度，也不意味着应解除节流。

若电脑每天只可用于采集 10 小时，同一模型需要至少约 52% 的有效 304；8 小时则约需 64%，且尚未预留故障余量。全天在线时零缓存可能装入 24 小时，若候选增多或休眠数小时就容易积压。能否稳定日更必须同时报告“单批时间”和“每天实际可运行时长”。

## 改善项及收益边界

|优先级|改善|为何保留覆盖|预期收益与限制|
|---|---|---|---|
|高|先读当天种子并建立可证明的第 20 名下界，再据此全站搜索及必要扩围|仍需覆盖所有总星可能达到当日门槛的仓库，不能只采昨天名单；最终门槛复核及下降后的补采保留|直接减少昂贵历史读取，优于调并发；数学边界见独立 bounds-analysis|
|高|真实条件请求与完整跨日指标|所有候选仍得到本次服务端校验；失败不沿用旧数据冒充成功|已经实现；需验证命中率及周切换，不能事先承诺节省比例|
|中|复用已验证的分片边界，重新查询各分片并按需再细分|复用的是区间，不是昨天仓库名单；总范围连续、无空洞，重查分页/漂移/重复检查仍保留|减少从根重新试探的内部节点请求。本次快照有 36 个 split 节点，相对 264 次搜索约 14%；潜力约分钟到十几分钟/轮，通常不是十倍提速|
|中|让候选发现与已发现候选的历史读取交错执行；核心额度等待时推进搜索|最终仍完成全部分片和长时间读取后的独立复核，控制跨阶段一致性|可隐藏初次枚举的部分墙钟时间，约一小时量级；四线程池/锁/证据合同需隔离验证。不能用提前完成的第二轮搜索冒充读取后复核|
|中低|日榜只读取包含目标桶的最少周数，并长期保持相同参数|每次验证目标桶实际存在；迟到补采及周切换必须正确选页，不能把缺桶补零|减少正文及无关变动导致的缓存失效，但不保证减少请求。当前六周本来可供日/周/月共用；拆成多个请求可能反而增加总成本|
|低|减少每次启动进程、建立连接的开销，考虑同一调用内分页或复用连接|网络请求/页证据仍完整，认证边界不扩大|零缓存时主要受额度限制，不会把约 16 小时缩到 1 小时。先用保存数据测本地处理；实际连接优化需另做小样本对照，不应先改认证链路|
|低|304 正文解压/JSON 反序列化及 SQLite 聚合优化|仍按本次固定目标日桶重新评分并保留来源|本机 CPU 尚非主要瓶颈；只在 profile 显示成本明显时做|

搜索和核心读取使用不同主要额度，可在统一请求队列中交错安排，不能据此认定可以无限并发。GitHub 官方建议顺序请求降低次级限流风险；已有四线程也需以真实响应约束，不能把公布的最大并发数理解为推荐并发。[官方最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

当前限流器在发请求前会保守计入在途请求：当本地 4,000 次预算已满，可能连潜在 304 也等。不能因为“预计命中”就绕过额度门禁，因为请求也可能返回 200。合理的改进方向是利用真实响应头及小额保留预算做有界调度，而不是假定条件请求必然免费。服务端额度在区域间可波动，也不应按两次 remaining 相减精确计算消耗。[官方额度文档](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## 不建议的所谓提速

- 多建同一账号的 Token：用户级授权共享个人主要额度，不能凭多 Token 得到多个 5,000 请求预算。[官方额度文档](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- 把本地预算 4,000 直接提高到 5,000：理论额度量级最多从 16.49 降到 13.19 小时，却消耗为其他用途留出的空间，无法解决完整性或离线问题。
- 取消第二轮全量复核、只读昨日候选或只读 Trending：会降低发现新项目的能力或改变现有完整性合同。
- 用本地缓存、相同总 Star 数、`updated_at` 不变代替条件校验：这些不足以证明目标日桶未变。
- 无限加并发：不能增加主要额度，还会增加次级限流风险。官方对并发、频率和资源使用均有约束。[官方额度文档](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## 最小采用条件

保持当前采集作为对照。冷启动完成后，用保存的不可变响应离线验证候选剪枝与分区复用，确认同口径、同最终排名与并列结果；再在后续真实日批记录有效 304、实际墙钟时间、等待原因及新增候选数量。未经这一层验证，只能称“可行优化方案”，不能称“每天 6 小时已实现”。
