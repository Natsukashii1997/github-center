# GitHub 日榜：日更容量与免费提速结论

2026-10-22。本轮交付是只读研究与离线分析，当前采集继续运行，未切换算法、改参数或重启。

## 当前判断

有不新增付费服务、保留现有全站覆盖口径的提速办法，但尚未证明每天稳定完成。当前空缓存日榜预计 18–22 小时，只有在电脑持续可用、候选和额度没有明显恶化时才可能装入 24 小时；不能把这一估计当稳定能力。

全站继续指 GitHub 索引可见的公开仓库，包含 fork、没有人工主题池。任何优化保留末位并列、缺失不补零、末轮新鲜复核和必要补采，也保留“非同一瞬间全站快照”的已知边界。

## 推荐的四项优化

|优先级|具体做法|为什么不牺牲覆盖|收益边界|
|---|---|---|---|
|1：机制已有，先测真实收益|每天向 GitHub 校验旧响应，服务端确认内容未变时复用正文|所有候选仍有本次真实校验，失败不拿旧数据冒充今天成功|真实 304 免主要请求额度，但仍需联网；当前跨日命中率未知|
|2：最值得新增|先刷新几十到几百个可能高分的项目，用当天分数建立第20名门槛，再动态缩小必读范围|例如已有20个项目当天新增至少1000星，总星不足1000的仓库不可能入榜；全站搜索仍覆盖所有可能入榜者，等于门槛者保留，门槛下降必须补采|替换现有“昨日末位×80%”的保守起点，可减少多余请求；当前下界已接近样本末位，不能保证十倍提速|
|3：减少流程等待|复用已验证的搜索分片边界，今天重新取完整分页；交错进行候选发现与历史读取|复用切分方案，不复用昨天名单；保留长时间读取后的独立复核|通常省分钟到约一小时；不减少主要历史读取的额度成本|
|4：避免功能增加后重复采集|同一份历史数据同时算近1/7/30日榜，候选取三榜并集、每仓只读一次|每榜窗口与候选边界独立校验，没有假定日榜总是包含周/月榜候选|避免未来三套页面采三遍，不等于当前单日能再快3倍|

GitHub 官方确认，正确认证的条件请求返回 304 时不消耗主要额度，但仍需遵守其他请求限制。[条件请求与缓存](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)

历史接口按周返回日桶；一条响应可以覆盖多个榜单窗口。缩为单周能减少处理范围，但调用次数未必下降，还可能与未来周/月榜重复取数，优先级低于上述改进。[官方历史接口](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)

## 每日可能要多久：条件情景，不是实测预测

固定假设：65,946 个候选，每小时预算4,000次占额度请求，全局最多每0.25秒启动一次请求，四个读取工人，两轮搜索约2小时，采用前轮历史延迟样本。下面的命中率以**全部历史请求**为分母；新加入、无缓存的候选也在分母内。

|全部历史请求中真实304占比|理想调度量级，含搜索|
|---:|---:|
|0%|约18.5小时|
|25%|约14.4小时|
|50%|约10.2小时|
|75%|约6.6小时|
|90%|仍约6.6小时|

模型为：搜索时间 + max（全部请求的调度时间、网络延迟所需时间、占额度请求所需的预算时间）。它未包含失败、候选扩围、他人占用额度、休眠和请求顺序导致的额外等待。不是上述命中率下的完成保证。

高命中时仍需发出约6.6万次请求，按当前节奏，仅请求启动就需约4.6小时，所以不能推出“命中高就几分钟更新”。若下一日门槛更低、候选更多，整张表都要重算。

周切换还可能使响应中的周列表整体前移，导致没新增Star的仓库也不再返回304。这是按官方响应结构作出的推断，尚未实测；现有周中三个统计日不能覆盖这项长期稳定性风险。

## 不采用的捷径

- **只抓 Trending、昨天上榜项目或最近更新仓库**：会漏掉新热点或长期不提交但突然涨星的项目。
- **总星不变就跳过**：新增500、取消500后总星可以不变，日新增却不是零。
- **把旧日桶当永不增加的上界**：虽然官方解释Star移除会删除原记录，但没有“所有历史日已结算、不会补写”的完整保证，当前不能据此无条件跳过校验。[官方实现说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)
- **直接改用 GH Archive／ClickHouse／OSSInsight 的快速榜单**：可帮助选种子，尚不能替代同口径全站覆盖。GH Archive 来自 Events；该时间线有数量窗口和延迟，事件计数与当前存续Star日桶也有差异。[GH Archive 来源](https://www.gharchive.org/)、[GitHub Events 边界](https://docs.github.com/en/rest/activity/events#list-public-events)
- **多开同一账号Token、无限增加并发**：不会自然增加用户主要额度，还可能触发额外限制。[官方额度规则](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

## 当前执行决定与下一步

当前采集保持原样，先得到真实冷启动耗时与完整结果。用户最新要求“先别中断当前采集”已经同步到本会话自动跟踪；原计划历史评分阶段主动中断测试延后，不会为了测速或研究停止正常进程。历史评分恢复仍标为待验证。

冷启动完成后，用保存的原始数据比较“当前固定门槛”和“当天种子优先+动态门槛”，先证明同窗口Top20含并列一致、所有排除范围可解释，再决定是否切换后续版本。当前研究没有授权自动替换采集算法。

原定连续三日继续记录：每批实际耗时、有效304比例、候选数量、额度等待、延迟与积压。只有每个固定窗口按计划周期完整完成，才支持“这三日跟得上”的结论；不能外推为长期保证。
