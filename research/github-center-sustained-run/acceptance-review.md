# 日榜全量采集与连续 3 个统计日：有限验收合同

审查日期：2026-10-22（北京时间）。本报告仅基于前轮已保存的日桶、月榜完整性及恢复证据做独立分析；没有新增网络请求，没有启动任务、注册自动化或修改采集代码。

**目标：先证明一个固定日榜能够找齐候选、计算 Top 20 含末位并列，再用三个相邻统计日的真实运行记录，判断现有电脑能否按日交付，以及缓存和中断恢复实际有什么作用。** 注册调度、进程启动、同日反复成功都不等于三日验收。

## 1. 固定范围与时间表

统计范围为 GitHub 搜索索引可见的全部公开仓库，包含 fork；无语言、项目类型或人工精选范围限制。结果为官方日桶中创建、读取时仍存在的 Star。Top 20 包含第 20 名的所有并列，不能只截断前 20 行。

| 阶段 | 统计日展示标签 | 固定桶键 | 最早计划开始时间（北京时间） | 是否计入连续 3 日 |
|---|---|---|---|---|
| 冷启动 | 2026-10-20 | (1792281600, 2) | 当前授权后开始 | 否 |
| 验证日 1 | 2026-10-21 | (1792281600, 3) | 2026-10-23 16:15 | 是 |
| 验证日 2 | 2026-10-22 | (1792281600, 4) | 2026-10-24 16:15 | 是 |
| 验证日 3 | 2026-10-23 | (1792281600, 5) | 2026-10-25 16:15 | 是 |

这是以当前观察到的 UTC 日历映射为基础、延迟两日标签的工程试验。16:15 北京时间相当于 08:15 UTC，距该统计日假定结束约 32 小时 15 分钟；**不能写成“结束后至少 48 小时”**，也不能写成 GitHub 官方保证的完成日。继续保留 `boundary_mode=observed_utc_mapping`、`completed_day_verified=false`。

每个批次在开始前冻结窗口，恢复时沿用原桶键。不能在长时间采集跨过午夜后，把剩余仓库换到新窗口。统计日标签与执行日不是同一个日期。

## 2. 冷启动与后续日更的可比边界

冷启动的枚举与用于正式评分的历史数据应重新联网取得，并保存到独立运行目录。旧月榜／样本只可用于产生同一窗口的探索下界，最终必须新鲜复核该下界；不得把旧评分直接记为本次已采集。

如果为节省额度复用前轮原始响应，这部分应明确计为“前置样本或热缓存”，并同时报告数量与原始时间。这样的运行仍可验证候选计算，但不能称作完全从空缓存开始的冷启动性能。推荐从空的日榜运行缓存开始，让首次成本与后续缓存效果有清楚基线。

后续每一天都必须重新枚举或完成能证明覆盖的候选更新。不能因为昨天仓库清单齐全，就把昨天清单当作今天全站。不同窗口的历史响应可以共享内容缓存，但新批次的评分必须按新桶键重算，并建立本次实际验证的新鲜度证据。

只有一个后台实例可以持有执行锁。同批次重复启动应恢复未完成工作，不增加一份正式榜单；不同批次不得误用只按仓库 ID 标记的“已完成”状态。

## 3. 每个日榜必须通过的覆盖与评分门槛

1. 搜索明确包含公开仓库及 fork。所有分片、查询条件、分页、接口完整标志、唯一仓库 ID 和实际范围可核对；密集同星值需继续细分，不能接受查询返回上限截断。
2. 动态上界只在实际同窗口分数支持下提高。每次排除的总星范围留痕；最终第 20 名经新鲜复读后，仍须支撑所有已排除范围。若门槛下降，恢复可能入榜的范围，而不是只改展示数字。
3. 所有未排除候选都有有效评分或可审计的排除依据。失败、缺日桶、身份不符、未取到页面均是未知，不能当成 0。仓库改名等以稳定 ID 对齐；结果来源需与候选 ID 相符。
4. 日榜检查的是 1 日分数的门槛，不能拿月榜第 20 名的门槛来缩小日榜范围。若门槛为 0，不得以总星至少 1 擅自去掉所有 0 分并列。
5. 入榜与临界候选进行新鲜复核；补核变化后的候选集合。第二次枚举若在历史读取完成前发生，须记录真实先后，不能称作“完成后复核”。
6. 复核候选总星与评分的上界反例。发现时间／口径不相容时保持未通过；未发现反例也不意味着上游索引绝对完整。

通过时的准确结论是：**在固定日桶假设与本批 GitHub 搜索索引采样范围内，全量候选读取和 Top 20 含并列排名验证通过。** 不升级为全 GitHub 同一瞬间的绝对完整快照。

## 4. 缓存指标必须分开记录

| 类型 | 算什么 | 不能推断什么 |
|---|---|---|
| 同批次断点命中 | 本批次已经成功的单元，恢复时不再联网 | 不能算跨日 ETag 命中或证明今日来源已更新 |
| 新批次 HTTP 304 | 在本次执行日真实发出条件请求，服务端确认内容未变；引用原始正文哈希与本次 304 响应时间 | 不能用旧文件存在或客户端未发请求冒充 304 |
| 新批次 HTTP 200 | 新响应正文独立保存；即使正文内容与旧版相同，也按真实 200 记录 | 不能因内容相同改记为额度节省 |
| 失败后保留旧缓存 | 旧数据仍在，但本次刷新失败 | 不能记为本次成功或用旧日期改成今天 |

跨日条件缓存命中率建议为：本次 304 数 / 本次携带有效缓存校验条件且得到 200 或 304 的请求数。另列所有尝试（含超时、429、5xx）、无缓存首次请求和未解决项，避免只保留成功分母。

HTTP 304 可能被调用工具报告为非零退出码，判定须依据实际 HTTP 状态以及是否存在可验证的对应正文，不能按退出码一律当失败，也不能遇到 304 却找不到正文仍算成功。

在三个真实执行日得到的 304 才是跨日缓存证据。同一日重复跑三次、请求后立即条件复查的命中率，只能作为协议和同日复查证据。

## 5. 中断、离线与延迟补跑怎样判定

在隔离采集运行中做一次受控中断，记录中断前已成功单元数、进行中请求与时间，恢复后核对成功单元未丢失、没有被重复计分或发布。进行中但未落盘的请求可以重新读取，须记录，不能要求绝对零重复网络请求。

已有“固定输入离线重放一致”的结果可作为对照，但本轮还需要真实执行进程的中断续跑记录。没有自然睡眠／断网事件时，只能称受控进程中断恢复通过，不能写成已验证所有电脑休眠场景。没有必要为了测试改全局电源设置或主动关闭用户网络。

保留原计划时间、实际首次开始、最后完成、所有恢复与等待时间。离线后按未完成窗口顺序补跑，不能跳过失败窗口、推进完成游标或与新窗口混写。

若冷启动拖过验证日 1 的计划时点，日 1 记录为延迟启动。若电脑离线两天后一次补齐三个窗口，证明的是历史补采能力，**不证明三个执行日均按计划运行**。

建议工程容量观察线：每个日批能否在下一计划日的 16:15 前完成，作为“24 小时日更周期是否容纳本批”的诊断项；这不是未经用户确认的精确交付时刻 SLA。第 3 日对应的观察截止为 10 月 26 日 16:15。晚完成仍保留恢复结果，但“按日及时完成”该项不通过，不能通过后移计划时间修饰结果。

## 6. 最小记录与成功判定

每批记录以下字段即可支持决策，不必扩成产品遥测系统：

- 运行 ID、目标桶键、源码／算法版本、原计划时间、实际开始／完成／恢复时间。
- 全墙钟耗时、实际请求耗时、限流等待、离线／进程中断等待；无法区分的时间标为未知，不强造“活跃运行时长”。
- 候选分片数、枚举唯一 ID 数、动态排除范围、有效评分数、未解决数、最终第 20 名门槛、并列数量、两轮差异与界限复核结果。
- core／search 各自请求数和响应额度；200、304、超时、429、5xx、重试、同批次断点命中分别计量。不用两次 remaining 相减代替总请求量。
- 不可变原始响应或其内容寻址对象、每次校验响应元数据、评分来源哈希、最终榜单快照。新鲜复读不能覆盖初始原始证据。
- 本批是否完整、是否在日更周期内完成、是否延迟补跑、是否含真实中断恢复，以及限制说明。

**冷启动通过**：覆盖与排名门槛闭合、所有候选已解决、原始证据可重算、真实耗时和请求量可核对。

**三个统计日运行验证完成**：三个固定目标窗口都已得到终态记录；每个目标都由其真实执行时点的请求／校验证据支持；没有跨日混窗或用旧结果冒充新结果；至少一次真实进程中断恢复已检查。完成验证可以得出“不满足稳定日更”，不要求为了凑成功而不断替换样本日。

**按日运行能力通过**：除上述条件，还须三个日批均在各自日更观察周期内完整完成，且自动触发、等待限额、恢复和缓存效果有真实记录。此结论仍只适用于这三日、当前电脑和账户，不等于长期 SLA 或正式产品验收。

## 7. 有限停止与权限边界

范围只到一次冷启动和三个固定统计日的验证。完成后停止采集与本次跟踪，不自动延长成永久监控。若三日出现失败，报告失败及影响，不静默换成后续三天直到通过。

额度不足时保存状态并等到允许重试时间，遵循响应 Retry-After／reset，不主动耗尽账户额度作为实验。为用户其他用途保留预算；鉴权失效、持续无法解释的身份／数据错误或必须新增费用／外部权限时停止相关动作并报告，不读出 Token、不上传本机认证资料、不换多个账户规避限额。

允许的范围是现有电脑、现有正常 GitHub 认证、公开数据读取、隔离本地证据和本次有限跟踪。禁止公开仓库、云端上传、付费服务、扩大私有数据读取、永久修改系统电源策略或未经授权持续采集。
