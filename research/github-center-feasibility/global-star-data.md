# GitHub 全站涨星数据可行性核验

核验时间：2026-10-22 17:40–17:51（Asia/Shanghai）；UTC 09:40–09:51。本分支匿名核验至 17:48；根代理补充认证预检与 Top 1 小候选实验至 17:51。

## 结论

**免费取得官方热门榜、面向全站的高星搜索、近期新建仓库搜索，以及单仓库历史 Star 数据，已经拿到实际成功响应。严格的全站 24 小时／7 天／30 天涨星 Top 榜，尚未完成可行性证明，不能宣布已解决。**

这不意味着必须把产品改成个人自选项目池，也不意味着必须逐个扫描 GitHub 的所有仓库。存在一条值得验证的免费路线：利用增长量不超过当前总 Star 的数学上界，从全站动态发现所有可能入榜的候选，再计算涨星。**本分支实测“三仓同口径历史 → Top 3 下界 B → 全站候选规模”，获得 B=4,422、候选约 14,767 个；根代理进一步完成了同一已结束官方周、22 个候选的 Top 1 小闭环。**后者以 GitHub 搜索索引和本批采样时点为证明边界，不代表滚动日／周／月完整 Top N 已实现；更多分片、窗口和持续运行仍待验证。

本轮没有执行全站仓库逐个扫描、注册服务、付费请求或部署。本分支全部匿名；根代理通过本机已登录的正常 gh 客户端复用现有认证做只读请求，没有读取、打印或复制凭据，也没有新增授权。

## 两个必须纠正的口径

**Trending 排名不能直接改名为涨星排名。** 本次官方周榜第 5 项 `android/skills` 显示 +1,332，第 6 项 `NationalSecurityAgency/ghidra` 为 +5,769，第 7 项 `debpalash/VoiceStudio` 为 +15,125。把这 17 项重排，只会得到“这 17 个上榜项目之间的增星排名”，不能补齐未上 Trending 的项目。[官方周榜](https://github.com/trending?since=weekly)

**当前总数、历史新增存续数、净增和事件数不同。** 官方新历史接口按自然周及日聚合，时间边界不保证与 UTC 对齐；工程说明指出底层 Star 记录在取消 Star 后会被移除。它不能被直接解释成完整加星／取消账本。净增需要两个时点的总数差；历史接口日粒度也不能无条件叫北京时间精确滚动 24 小时。上述字段可用，但产品名称必须对应实际口径。[历史接口](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)、[官方工程说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)

Star History 本次公开周榜的页面区间是 **2026-10-14 至 2026-10-20**。例如 `morluto/rea` 显示 +133,434；本次官方 Trending 周榜为 +129,417。统计区间不同，不能据此认定其中一方错误，也不能混合排序。每天重新抓取旧区间的周榜，不会把它变成每日重新统计的滚动 7 天榜。[Star History](https://www.star-history.com/)

## 可保持全站目标的候选路线

以下是独立分析与待验证方案，不是已完成实现：

1. 先从官方热门等来源发现项目，再用**同一指标、同一窗口**实测这批项目的增长量，得到 Top N 中第 N 名的一个正数下界 B。不能拿第三方自然周数值和官方当前周数值混合生成 B。
2. 对“周期净增”或“在周期内新增且当前仍保留的 Star”，增长量不会大于该仓库当前总 Star。因此，当前总 Star 小于 B 的仓库不可能超过已知第 N 名。
3. 从 GitHub **全站**搜索所有当前总 Star 大于或等于 B 的公开仓库，包含 fork，按 Star 区间及必要的创建时间进一步分片，处理单次搜索最多返回 1,000 条的限制。出现 `incomplete_results=true` 时该分片不能被视为完成。
4. 对所有符合界限的候选获取相同口径的历史数据，再计算最终 Top N。B 是随当天真实排名变化的界限，不是固定高星门槛，更不是人工精选名单。

最初用**演示阈值 5,000**作规模观察，全站搜索返回约 12,839 个候选；这个固定阈值试验本身没有实测 Top N 的 B，随后才完成下述动态下界实验。假设每个候选一次历史请求足够，则是约 12,839 次单仓读取，另加搜索分片及重试，而不是对本次广泛搜索中数千万个仓库逐个读取。**这个估算只说明路线值得试，不证明全天三个周期的完整候选规模、接口额度和运行时间都能满足。**

### 追加的小链条实测

为避免把固定 5,000 门槛当成真实 B，追加 4 次匿名请求：对 `morluto/rea`、`debpalash/VoiceStudio`、`anthropics/claude-plugins-official` 分别读取 5 个周桶，再做一次由实测 B 决定的全站搜索。

选择三个响应共同存在、且已结束的最新完整官方周桶 `week=1791676800`（时间戳的 UTC 展示为 2026-10-11 00:00；不据此宣称日界保证为 UTC）。每个仓库均核对 `total = sum(days)`：

| 仓库 | 该周桶内创建且当前仍存续的 Star |
|---|---:|
| morluto/rea | 232,274 |
| debpalash/VoiceStudio | 16,279 |
| anthropics/claude-plugins-official | 4,422 |

这三个值使用同一指标与同一周桶，所以全球 Top 3 的第 3 名增长至少为 4,422。查询 `stars:>=4422 fork:true` 得到 **14,767 个候选**，响应没有标记超时不完整。本次只取 1 项并观察总数，没有全枚举，不能据此宣称全球 Top 3 已算出。

这个实验验证了界限的形成与候选发现请求，不验证完整榜单。为了不猜官方日界，实验主动使用一个明确已结束的完整周桶；它**不是用户要求的最近滚动 7 天**，不能拿它冒充该功能验收。证据为 `dynamic-bound-history.json` 和 `dynamic-bound-result.json`。

### 根代理独立追加：完整小候选 Top 1 闭环

根代理复用已登录的 gh 客户端，首先实际确认普通认证 core 额度为 5,000、search 为 30，并成功读取同一个公开仓库的历史记录。这证明现有只读认证可用；没有新增身份、读取或复制凭据。证据：`evidence-ai/github-authenticated-read-probe.json`。

随后只验证上述已结束官方周桶的 **Top 1**，而非 Top 3 或完整榜单：

1. 用种子 `morluto/rea` 的 232,274 得到 Top 1 下界，搜索 `is:public stars:>=232274 fork:true`，返回 22 个候选，`incomplete_results=false`，本次一页完整返回。
2. 22 个候选的历史查询全部成功，且都包含同一周桶。但领先项目复读为 232,273，较种子少 1，导致最初的严格下界条件失败。这个首败保存在 `probe-result-initial.json`，没有被成功结果覆盖。
3. 将候选界限保守降到 230,000，重新全站搜索；候选仍是同一组 22 个，没有新项目需要补读。再次读取领先项目，仍为 232,273，满足 `赢家值 >= 230,000`，因此在该查询索引与本批采样的边界内完成 Top 1 论证。

这是“同口径界限 → 完整小候选集 → 全候选计算 → 边界检查 → 首败修正”的实际闭环。证明边界仍是 GitHub 搜索索引可见仓库及本批时点；不能独立证明上游索引零遗漏，也不能消除后续采样中的 Star 回撤与索引变化。阈值内第二、第三名没有全球排名含义。证据：`evidence-top1/probe-result.json`、`candidate-search-rechecked.json`，及保留的初始失败记录。

### 免费额度下的请求量下界

下表是按 12,839 个候选、每仓一次历史查询的假设做的额度换算，**不是实测耗时，也不是当前目标的实际规模**。搜索结果若有索引遗漏或实际 B 更低，工作量会改变。

| 项目 | 请求量下界或额度换算 |
|---|---|
| 单仓历史 | 至少 12,839 次；同一次若能取足 6 个自然周，可作为近 1／7／30 统计日的共同原料，不必为每个窗口各读一遍 |
| 候选枚举 | 每页最多 100 条，至少 129 个结果页；单查询最多 1,000 条，至少拆成 13 个非重叠完整分片，实际还会增加探测查询 |
| 本次匿名 core 限额 | 响应头实际为 60 次／小时；12,839 次约相当于 213.98 个小时额度，约 8.92 个 24 小时额度，因此匿名单额度不足以每日重算该示例规模 |
| 普通用户认证 REST 基础额度 | 根代理本次实际确认 core 为 5,000；按每小时基础额度计算，12,839 次约占 2.57 个小时额度、需至少 3 批小时额度；约占 24 小时基础额度的 10.7%。不是承诺 2.57 小时跑完，窗口重置、二级限流和响应时间另计 |
| 搜索额度 | 129 页按匿名 10 次／分钟折算为 12.9 个分钟额度，按认证 30 次／分钟为 4.3 个分钟额度；分片探测和重试还要额外计入 |

普通认证不等于购买 GitHub 付费套餐。根代理已通过正常 gh 客户端验证现有身份与额度可用，无需让用户另外交 Token；本分支的 19 次请求尝试仍全部匿名。重试、数据复核、时间边界补读、项目详情读取及首次存储都没有包含在上述最小量中。实际运行还受其他共享额度使用影响。[官方频率限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[搜索限制](https://docs.github.com/en/rest/search/search)

追加真实下界 B=4,422 的实验对应 **至少 14,767 次历史读取＋148 个枚举结果页**（假设一仓一次历史请求足够，尚未包含分片探测）。匿名额度约相当于 246.12 个小时额度；普通认证额度约相当于 2.95 个小时额度、至少 3 批小时额度，约占 24 小时基础额度的 12.3%。这些仍是额度当量，不是实测运行时间；全局 Top 20／100 及最近 1 天的下界可能更低，需要更多候选。

决定性未验证项：

- 完成全局搜索分片后，是否仍存在搜索索引限制、超时、密集同值分页或时间漂移造成的漏项。
- 24 小时榜的第 N 名增长下界可能更低，候选数量可能明显扩大；本次未测这个规模。
- 采用“历史新增存续 Star”还是严格净增，必须与需求中的“新增 Star”一致。严格净增还需可靠历史总数；新进入候选界限的项目可能没有旧快照。
- 因为历史接口可直接补历史，优先验证“当前仍存续的新增 Star”路线；如果只能获得近 1／7／30 个统计日，必须作为候选口径说明，不能擅自将用户的滚动 24 小时／7 天／30 天要求替换掉。
- 根代理已验证现有认证与小候选全读闭环；认证额度下的大规模持续运行、失败重试、日期边界和每日刷新尚未实测，不能由小样本成功推断长期稳定。
- GitHub 本次已实际出现 `incomplete_results=true`，因此“HTTP 200”不能等同“统计完成”。

官方搜索支持的排序是总 Star、Fork、帮助问题数及更新时间，没有周期增星排序；每次搜索最多返回 1,000 条，且提供不完整标记。因此没有通过本次所查官方接口直接拿到一个“全站近 7 天增长榜”。[官方搜索说明](https://docs.github.com/en/rest/search/search#search-repositories)

## 对当前项目的判定

| 能力 | 判定 |
|---|---|
| 官方热门日／周／月榜入口 | 免费可行；本次周榜已实取，其余周期未在本轮重测 |
| 全站累计高星与近期新项目入口 | 免费数据路径已实取；需处理搜索结果不完整、分页和候选时间范围 |
| 单仓历史 Star 作为计算原料 | 匿名接口已实取；新接口可以补历史，不必错误地声称只能从今天开始积累所有历史 |
| 外部公开周涨星榜聚合 | 免费读取已实取；必须保留来源、区间和源更新时间，覆盖完整性未证实 |
| 已结束官方周的小候选 Top 1 | 根代理已完成 22 候选的小闭环；范围为 GitHub 搜索索引与本批时点 |
| 精确全站 24 小时／7 天／30 天涨星 Top 榜 | **免费算法路线已有小闭环证据，完整 Top N 与持续交付尚不能承诺** |

建议下一项最小验证只针对“全站 7 天 Top N 候选完整枚举与计算”，先固定指标、时间边界和 N，再跑完动态界限内的候选并保留分片完成证据。如果该验证失败，应报告失败边界和实际投入，而不是把有限结果冠以全站榜，或要求用户默认接受个人项目池。
