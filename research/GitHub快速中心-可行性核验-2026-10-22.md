# GitHub 快速中心：全站涨星与免费 AI 日报可行性核验

核验日期：2026-10-22。范围：公开数据与现有本机能力的有限实测。没有进入产品开发，没有安装软件或模型，没有注册定时任务、购买服务或发布内容。

## 结论先行

| 核验对象 | 判定 | 本次证据 | 仍不能承诺 |
|---|---|---|---|
| 不新增模型 API 费用的中文日报 | **单次生成已跑通** | 本机现有 ChatGPT 登录的 Codex CLI，处理 5 条真实公开榜单记录，39.64 秒生成；字段检查和独立内容审查通过 | 无限免费、完整日批质量、每日无人值守稳定运行、整站永久免费托管 |
| 面向 GitHub 全站的涨星排名 | **免费路线获得小闭环实证，完整需求仍为条件可行** | 官方历史接口实际可用；现有 GitHub 认证每小时 5,000 次基础读取额度；基于全站搜索索引完成一个已结束官方周的 Top 1 候选枚举与计算，22 个候选全部核验 | 上游索引绝对零遗漏、精确滚动 24 小时／7 天／30 天完整榜单、大规模每日稳定更新 |

**保持已经确认的全站目标，不退回个人收藏池或人工精选项目池。** 但不能把本轮小规模成功扩大成完整产品已验证。

## 一、全站涨星数据

### 已经实取的免费数据

- GitHub 官方 Trending 周榜：可取得排名、总 Star、页面显示的本周 Star。实际存在相邻项目增长数逆序，因此官方 Trending 排名不等于按涨星严格排序。
- GitHub 全站仓库搜索：可以按当前总 Star 排序，也能限定近期创建；其中一次实际响应带有 `incomplete_results=true`，必须按未完成处理，不能只看 HTTP 200。
- 官方单仓库 Star History：匿名和现有认证均取得成功响应，提供按周及日聚合的数据。
- Star History 的公开周榜：可以作为一个来源读取，但来源覆盖与统计区间不等于我们自己的完整全站增长统计。

依据：[GitHub Trending](https://github.com/trending?since=weekly)、[仓库搜索](https://docs.github.com/en/rest/search/search#search-repositories)、[Star History 接口](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)、[Star History 网站](https://www.star-history.com/)。

### 不必逐个扫描全站的原因

对“某周期内新增加、目前仍保留的 Star”，该数值不可能超过项目当前总 Star。

因此可以先用真实项目得到第 N 名的一个增长下界，再从 **GitHub 全站** 找出所有总 Star 足以超过这个下界的仓库，逐一计算。界限随真实数据变化，不是人为设置固定高星门槛，也不是只在已有收藏中排名。

本轮做了两个级别的验证：

1. **规模验证：**三个项目在同一已结束官方周桶中的增长分别为 232,274、16,279、4,422。因此，那个周桶的全球第三名至少达到 4,422。全站查询得到约 14,767 个可能进入竞争的项目；这批没有全量枚举和计算，不能据此宣布全球前三已算出。
2. **完整小候选验证：**仅验证同一个周桶的第一名。将候选界限设为 230,000，全站公开仓库搜索（包括 fork）返回 22 个项目，全部取到了同一周的历史值。领先项目的复读值为 232,273，满足界限条件。它验证了这条算法路线能闭合，而不是只验证接口能返回数据。

第二项证明以 **GitHub 搜索索引可见范围和本批采样时点** 为边界。搜索接口没有报告不完整，不等于独立证明 GitHub 索引零漏项；这也不是各接口共享同一瞬间的原子快照。

本次还保留了一个实际问题：最初种子值为 232,274，复读少了 1，原定严格阈值检查失败。随后保守降低界限、重新枚举并复读，才确认检查通过。原结果没有被成功记录覆盖。少 1 星本身不证明原赢家错误，但说明历史计数会变化，边界附近需要复核。

### 免费不等于采集工作量很小

现有 GitHub 登录已经验证可用，无需新购套餐或向聊天提交密钥。实际基础额度为每小时 5,000 次，搜索为每分钟 30 次。

以上述 14,767 个初始候选全部读取为例，在每仓一次历史读取足够的假设下，需要 14,767 次历史请求与至少 148 个搜索结果页，尚未计入搜索分片探测、补读和重试。历史读取量约相当于 **2.95 个小时额度**，不是承诺能在 2.95 小时内完成。Top 20／100、近一天窗口的界限可能更低，工作量可能更大。

这也不是所有算法都无法降低的请求下限：可以按总 Star 从高到低计算，随着真实第 N 名的分数升高而提高界限；剩余项目的总 Star 都低于当前第 N 名时，就可以提前停止。该优化尚未实测，不能直接据此承诺更小的运行成本。

因此费用上存在免费路径，但还要验证全量分片、限流、电脑在线时间和稳定交付，不能凭这次 Top 1 小实验认定每天三张完整涨星榜都能完成。

依据：[官方接口限额](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)、[搜索分页与不完整结果](https://docs.github.com/en/rest/search/search)。

### 时间和涨星口径：用户已确认，技术边界继续核验

- 官方历史接口提供按日／自然周聚合的数据，日界线不保证与 UTC 对齐，不能直接称为北京时间精确滚动 24 小时。
- 官方工程说明指出，取消 Star 后底层记录会被移除，所以历史值表示当前仍保留的相关 Star，不是完整新增事件账本，也不等于两个时点总数相减的净增。
- 要做到严格净增，需要可靠的两个时点总数。新进入候选集合的旧项目，未必有我们自己的过去快照。

**用户已确认按 GitHub 官方统计日计算近 1／7／30 日涨星榜，每天更新，优先不新增费用。** 本轮继续以官方历史接口的新增存续 Star 为口径。官方未提供“已完整统计到哪一天”的字段，最新日桶的截断方式仍需技术核验；不能因为用户批准统计日，就声称接口提供了完成标记。后续实测见同目录 `github-center-daily-validation`。

依据：[历史接口口径](https://docs.github.com/en/rest/activity/starring#get-repository-star-history)、[GitHub 官方实现说明](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)。

## 二、不新增模型 API 费用的 AI 日报

### 当前最实际的路线

使用本机已经安装并通过 ChatGPT 登录的 Codex CLI：

**确定性采集榜单 → 保存事实数据 → Codex 生成中文解释 → 核对数字和来源 → 保存成品 → 网站读取同一份日报。**

这使用现有账户的可用额度，不另接付费模型 API；不等于无限免费，也不等于订阅能直接当网站模型 API 使用。成员浏览成品不会各触发一次生成。

Codex CLI 支持非交互输入、结构化输出和复用保存的登录。AIHOT 可以借鉴后台生成、结果缓存和去重机制，但 Codex CLI 不是 AIHOT 现成的模型 HTTP 接口，需要一个受控的生成适配步骤。

依据：[Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)、[认证方式](https://learn.chatgpt.com/docs/auth)、[AIHOT 模型配置](https://github.com/KKKKhazix/AIHOT/blob/main/site/models.ts)。

### 本次实测

| 项目 | 实际结果 |
|---|---|
| 本机条件 | Apple M5、24 GiB 内存；Codex CLI 0.160.1；ChatGPT 登录有效 |
| 本地模型 | 没有发现常见本地模型程序或可用服务；没有安装新模型 |
| 输入 | 今日实取的官方周 Trending 前 5 项，其中一项简介为空；不是完整今日榜单 |
| 运行 | 隔离目录、临时会话、只读、只使用输入材料；未提供额外 API Key，没有调用工具 |
| 生成 | 退出码 0，耗时 39.64 秒，得到结构化中文结果 |
| 数据核验 | 40 项检查通过：项目、顺序、数字、时间窗、来源、空简介处理和运行状态等 |
| 独立内容核验 | 通过；没有编造昨日变化、连榜天数、涨星原因或使用效果，作者宣传保留归因 |
| 本次返回用量 | 输入 30,505 tokens，输出 1,167 tokens；消耗现有 Codex 额度，没有据此推算货币费用 |

本轮没有测试完整四榜合并、跨日变化、完整日批、额度耗尽恢复或连续定时运行。电脑离线或额度不足时如何延迟补跑，仍需在后续原型中验证。

本地 Ollama 可作为后备：协议上可以接入 AIHOT 的兼容接口，但当前未安装。不能将 M5／24 GiB 直接等同于某模型的质量和性能已经合格，也不为本次验证另行下载模型。[官方兼容文档](https://docs.ollama.com/api/openai-compatibility)

## 三、对下一步的影响

1. **AI 日报可以按现有 Codex 额度路线继续设计。** 优先每天生成一次并保存；需要保留额度不足、电脑离线、内容校验失败的状态，不把旧日报标成今天生成。
2. **全站目标与统计日方案已确认，继续核验近 1／7／30 日联合采集、搜索分片、实际容量和运行恢复。** 全量实验需要保存每个搜索分片的完成证据，不能从小样本通过直接进入“全站日周月榜已可靠”的承诺。
3. **不新增付费服务。** 当前两个方向都有可用的现有免费能力；尚不能因此保证完整产品和长期托管都是零成本。

当前交付是可行性研究与隔离实测证据。没有产品代码、正式部署或持续自动化验收。
